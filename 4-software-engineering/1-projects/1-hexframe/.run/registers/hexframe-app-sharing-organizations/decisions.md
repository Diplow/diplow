# decisions, hexframe app Sharing & organizations

### DEC-1 Mapping takes `{ actor, system }`: the System named by its star, found by its owner, checked once in `reached`

HEX-124. Every read and every change of Mapping's service takes `Acting`, `{ actor, system }` (`domains/mapping/mapping.ts`). `system` is the star's id, a string, as the ticket says a System is named and as later tickets will receive it from a request (a Handle is a star's id). `actor` is `{ owners }`, the opaque ids it stands for, an Account's own alone for now: the only thing the check reads. HEX-125 gives it the Account and its Groups when `may` needs them, and moves it to `entities/` beside `may`, since `operations/` will read it there. Until then it stays a type of the service, because `entities/` holds five files and the door has no reader for it.

The check is one function, `reached(acting)`: it reads the owner the star names (`Tiles.ownerOf`, one lookup on the table's key) and answers it when the actor stands for it, `TileNotFound` otherwise, a star that names nothing included. Every read and every change asks it first, then passes the owner it answered to the repository, which finds a System's rows by its owner, as before by the Account. The lock is still the owner's Root, which is the star. A System the API layer pairs with its own idea of the owner was the other way, with no lookup per call: refused, because the pairing would be trusted, where `reached` checks it against the table on every call, and because a later ticket that names a System from a request would have needed a second, minting step.

The API layer resolves both in one function, `actingOnOwn(account.id)` (`api/mapping/programs.ts`): the actor `{ owners: [account.id] }` and `Mapping.starOf(account.id)`, the Account's star, its Root added untitled on the first read, as `system` and `locked` used to add it. Assistant's programs and the bus's recording call it too, and Mapping's tests build the same pair in `testing.ts`. Mapping finds the star; whom an Account stands for is IAM's to say, so the actor is built in the API layer, where HEX-125 adds Groups in one place (cubic's local reviews on #141, whose first round had moved it into Mapping and whose third moved it back). `Tiles.root` now reads before it inserts, so the poll behind `latest`, which now resolves the star too, writes nothing. Each request makes one or two more small queries than before (the star, then its owner), the cost of the seam. `reached` can fail, so the lists of errors `system`, `conversationDay` and `latest` may fail with now include `TileNotFound`, which `api/mapping/mapping.test.ts` and `api/assistant/assistant.test.ts` pin. It can't happen while the API names the Account's own System.

`tile.account_id` is renamed `owner_id`, and its index `tile_ownerId_idx`, by `migrations/20261017191758_tile-owner`, a rename that keeps every row. `tile_root_idx` keeps one star per owner. The database's rule asks a migration on `main` to keep the code before it working. A rename doesn't: between the production build's migration and the new code going live, the old code's queries name a column that no longer exists. The add-backfill-drop way was refused for this run: its window either loses the rows the old code adds (owner null) or leaves the old code's writes refused, and it leaves a dead column for a later change that no ticket of this project owns. The app has no user but Ulysse before launch, and `turn-key-turn-only` dropped a column the same way. Whoever merges `project/sharing` into `main` sees the window here.

`readTile` moved from `mapping.test.ts` to `domains/mapping/testing.ts`, which sat at 599 of its 600 lines. The new case, an actor naming another Account's star or a star of nothing, refused `TileNotFound` on every read, on a change and on `changing`, the import's path, with the owner's System untouched, is in `api/mapping/mapping.test.ts`, where the service's cases go when `mapping.test.ts` is full (`hexframe-app-optimistic-writes-and-patterns/decisions.md#DEC-13`).

### DEC-2 Rights per Tile: Grants resolved in `entities/rights/`, `may` and `allowed` in `operations/rights/`, asked before `decide`; the System whole stays its owner's

HEX-125. The values, `Grant`, the `Actor` and the resolution are entities (`entities/rights/rights.ts`); `may`, and `allowed`, what each Operation needs, sit beside `decide` in `operations/rights/may.ts`. Both are folders of their own: `entities/` held five files and `operations/` five, with `decider/` at five too, so a file and its test would have made seven. The service's tests over PGlite are `operations/rights/shared.test.ts`, since `domains/mapping/` holds six files, as `operations/batch/batch.test.ts` sits beside its fold.

`Actor` moved out of `mapping.ts`, as DEC-1 said it would, and carries the Account, its Groups, the owners it stands for and whether a Session proves the request (the ticket's comment of 2026-10-17). The API layer builds it in `actingOnOwn` alone, whose every caller says whether a Session proves it, a required field (cubic's second local review on #142, after a default of none had refused the user's own Undo): a server function or an MCP call passes what its proof says (`forAccount`, from IAM's `signedIn`); the user's Undo, behind `sessionOnly`, passes one; the Assistant's other programs and the bus's recording pass none, an accepted Proposal's writes among them, since they are published as its Turn's until HEX-135 makes them the user's. So the owner's move that would open a Tile is refused an agent, as the rule wants. Groups are `[]` until IAM has them (HEX-137).

The service asks `allowed` on the System it locked, with the Grants read under the lock, then `decide`, so a slot taken or a stale Version never tells of a Tile the actor can't read: without *read* on a Tile the Operation names, `TileNotFound`; any other lack, `NotAllowed`, a Tile set to *none* inside a deleted subtree included, which never says which. Every change makes one more query, the System's Grants. A read from one Tile (`readTile`, `openTile`, `titles`, `glimpses`, `ownTile`, `summary`) answers as before for the owner, with no query more; for anyone else it reads where every row stands and the Grants (`Tiles.places`, `Tiles.grants`), refuses a Tile they can't read `TileNotFound`, leaves out what below it they can't read, and what stands under that, and gives no parent when they can't read it. A Reference to a Tile they can't read shows broken until HEX-133 makes it unavailable. `titles` and `glimpses` leave such ids out rather than refuse: a star's existence is no secret, its card being anyone's.

A read of the System whole (`system`, `systemVersion`, `exportTile`, `systemFiles`, a read through a batch), a batch (`addToBatch`, `runBatch`, `undo`) and an import (`changing`) keep `reached`, the owner's alone, `TileNotFound` to anyone else. The other way was to ask `may` for every Tile they touch: refused, because HEX-126 replaces the whole read with one filtered for the actor, gaps marked, and a check now would be thrown away; and a batch decided across rights needs `may` threaded through `fold` and `undone`, which HEX-134, a Turn on someone else's Tile, is the first to need. `runOperation` goes through `operate`, so it asks `allowed` already.

A move or a swap widens when a subject holds on a carried Tile, after it, a right it didn't hold before: *read*, as the rule says, and *write* and *@* too, since a Group reading a Tile would otherwise write it once Bob moved it under a Tile the Group writes, by no Grant the owner set (cubic's local review on #142, P1). The subjects looked at are those the System's Grants name, and Everyone: one without a Grant anywhere reads nothing, the star giving *none*. A swap is two moves, each Tile under the other's parent. A move under a Tile it carries opens nothing, `decide` refusing it, and `valueOn` stops on a walk that comes back to a Tile it passed: the first draft of the check walked forever on the Root moved under itself, which `api/mapping/events.test.ts` makes. Only the owner from a Session widens. A batch and an undo, the owner's alone, are checked whole on the System they leave (`allowedBatch`): run without a Session, as every Assistant program runs, one that opens a Tile that stood before is `NotAllowed`, a Tile it makes opening nothing, so a Proposal or an undo can't do what the agent's own move could not (the same review, P2). An undo puts back a deleted Tile without the Grants its delete took with it, the table's key cascading, so a Tile set to *none* would come back inheriting (cubic's second and third local reviews on #142). Only a change without a Session is ever undone, an applied Turn's or an accepted Proposal's, so such a change may not delete a Tile carrying a Grant, nor anything above one (`dropsGrants`, in `allowed` and `allowedBatch`): no undo then has a Grant to put back. The other ways, Grants carried in a batch's inverse or Grants kept past their Tile, were refused: the first makes them part of what Mapping holds of a System, a change of the aggregate no ticket asks for yet, and the second goes against the ticket, whose delete takes its Grants. `addToBatch` refuses what `allowedBatch` would refuse, so a Proposal never holds a write its acceptance refuses. A test-only write (`tiles/testing.ts`) is fenced by dependency-cruiser's `no-program-importing-the-grant-write`, which `scripts/lint.test.ts` proves fires. A delete or a move over a Tile the actor can't read is refused `NotAllowed`, which says that something below is held back, never what nor where: the ticket asks for the refusal, the other way being to delete or carry a Tile the actor can't write, and HEX-126's gap marks show the same fact on the canvas.

Everyone gets *read* at most, held twice: `Grant`'s Schema refuses more, and the `grant` table's checks refuse the row. A row that is no Grant resolves for nobody, `grantOf` leaving it out. The table, `migrations/20261017201531_grant`, is new and additive, so the code before it keeps working while production migrates: one row per Tile and subject, unique with nulls not distinct, `subject_id` null for Everyone alone, its key to `tile` cascading, so deleting a Tile deletes its Grants and those below it. Its name is the ticket's; Drizzle quotes it, `GRANT` being a keyword. Inherit is no row. No program writes a Grant yet: the tests set theirs through `tiles/testing.ts` (`granted`), kept out of the repository's `Writes` so nothing but a test can change who reads what. HEX-128 adds the write, a Session's only, and the delete that puts a subject back to inherit.

`NotAllowed` is Forbidden. The MCP teaches it on every write, the message table words it in both languages, and the MCP's tool listing snapshot moved with the descriptions. Help and the tutorial are decided on before any right: an Operation naming them is decided on the shipped System, which `decide` refuses whoever acts. STACK.md, frozen for this run, already says a System's Tiles are read by their Grants, which Mapping decides, so nothing in it is out of date.

### DEC-3 The System as the actor may see it: `Seen`, the flat System with rights by id and its gaps, the star as its card; the MCP's reads on the System holding their Tile

HEX-126. `system({ actor, system })` answers a `Seen` (`entities/rights/seen.ts`, built by `seenBy`): the flat System as before, holding only the Tiles and References the actor may read, at the System's Version, with `rights`, the actor's rights on each Tile by id, the star's included, and `gaps`. Its owner's read is the System whole, in the one query it was, every right on every Tile and no gap, the Grants not even read; anyone else's reads the Grants beside the rows. The rights sit beside the Tiles rather than on them, so `System`, which `decide`, `evolve` and the client's overlay rule on, stays what it was and the client keeps one System for drawing and deciding; a Tile the overlay makes before the server answers has no entry yet, which HEX-127, the first to offer actions by rights, reads from its parent. The first half of MR-9, what you read is scoped to what you may see, is done; its second, Bodies split out of the canvas's read, stays out of the project.

**The star's card.** A star the actor may not read comes back as its card, its Title and Preview, its Body empty, its Version the first and nothing it keeps from its files (`carded`, the one rule of a card, on a Tile and on a row, and `cardOf`), its rights none. `readTile` and `openTile` from such a star answer the card too, and a read whose parent is the star names it by its Title; `titles` and `glimpses` show it. What an actor may read and is shown is read once, `sightOf`, and whether a row they come upon is shown them, `shownRow`, both in `seen.ts`, so `seenBy` and the service's reads from one Tile never disagree (cubic's second local review on #143); `ownTile` still refuses it, the card being no Tile they read. A star that names no System is `TileNotFound` everywhere, as before.

**The gap.** A Tile the actor may read under one they may not, the star aside, is a gap: it stands in `gaps`, by id, hung from the star with no parent nor slot, and what stands below it stays in `tiles`, under it. Its place is said nowhere, neither its parent's id, which would tell a hidden Tile exists, as the never list forbids, nor its slot, which would tell of that parent; that something stands between is what the ticket asks the "…" to show. So `tiles` keeps its meaning, every Tile where it stands under a Tile the reader sees, `systemOf` is unchanged, and `decide`, the overlay and every slot check never take a gap for a Child of the star (cubic's local review on #143, which found the first draft, a gap placed in the star's slots with its own, misread by everything but the tree). The client's `decide` may still think a slot free that a hidden Tile holds, which HEX-127 meets when it gates the actions. A Reference is shown only when the reader may read the Tile it points at, or it points at the star: one to a Tile kept from them would say that Tile's id, which DEC-2's reads showed broken, so `seenBy` and the reads from one Tile now leave it out (the same review, P1). A Reference under a Tile the reader may not read is left out too, meaning nothing without its holder.

**What stays the owner's.** The ticket asks the read "with its Version"; its owner's carries it as before. Anyone else's carries 0, and a card the first Version: a count of the System's changes, or of the star's, would tell a stranger that Tiles they may not read are there and moving, which the never list forbids (the same review). A visitor's poll is HEX-127's to work out. `systemVersion`, an export, a Turn's files and a read through a batch keep `reached` (`ownersWhole`): the ticket asks none of them, HEX-127's visit is the first to poll another's System and HEX-134's Turn the first to read one through a batch.

**Naming the System.** The server function `system` takes `SystemRead`, a star's `TileId` or nothing, the Account's own (`programs.ts`'s `systemAt`; `system` stays the own read every caller and test used). The MCP's `open_tile` and `map` read the System holding the Tile they are given: `Mapping.holding`, one join on the `tile` table (`Tiles.starHolding`), names its star, and the read asks `may` there, so a Tile kept from the Account is `TileNotFound`, as an id no row has, which reads the own System and finds nothing; a shipped id holds no row and is read by its id, as before. The request is proven signed in before any lookup. Both go through `onSystem`, where a Turn's Key never trades its own System for another, `TileNotFound` (the never list's Turn's Key bound to its System); a change still acts on the Account's own. That binding stays in the API layer, which names the System a request acts on (DEC-1), rather than on the actor as a System it is bound to, a change to Mapping's language left to HEX-134, whose Turn is the first to start elsewhere. The tests that compare the service's System with what `decide` and `evolve` make read it through `testing.ts`'s `held`, the read without its rights and gaps.

### DEC-4 A visit: `/t/<id>` leads to home with `system`, the star; the canvas and the corner across gaps; a visit looked at, not acted on, until HEX-132 and HEX-134

HEX-127. A link to a Tile, `/t/<id>`, is a route of its own (`routes/t/$id.tsx`) that asks the server where it leads (`visit`, `api/mapping/programs.ts`: the star of the System holding the Tile once Mapping's `shownTile` found the Account may read it, or that it is the star, whose card anyone sees, none for its own, `TileNotFound` otherwise) and redirects to home with `system`, that star, and `center`, the Tile. Home with `system` stays one screen: the visited System is a query of its own beside the Account's (`['system', 'read', star]`), drawn through the same `System` component, the corner from its star, the journey taking the canvas there and the mark home. The other way, a page of its own for a visit, was refused: it would have doubled home's chat, composer and widgets. A Tile the Account may not read answers the same "Nothing to see here" as one that doesn't exist; signed out, `/t/<id>` sends to home's sign-in with `redirect` back, a Tile Everyone reads being HEX-129's.

**Gaps.** A Tile the visitor reads below one kept from them is hung from the star in the canvas's tree (`TileNode`'s `gaps`, each `across`), drawn in none of the star's rings, since its place is not said (DEC-3), and reached by centering it; `pathTo` goes through it right below the star, so the camera, Back out and the corner work unchanged, the `Rail` drawing a "…" above a step reached across.

**What a visitor may do.** A visit is looked at, not acted on, for now: the canvas takes a `Reach` (`features/system/acting.ts`), `owned` on the Account's own System, every line, `looking` on one visited, where a Tile's menu keeps the lines that go somewhere and Copy, and no free slot, move, swap, agent's line, export or import is offered, whatever Mapping's Grants give the visitor. Every write the page sends acts on the Account's own System, `changeForAccount` naming no other, so a writer offered Edit would be offered a `TileNotFound`; and a Turn starts at home alone. HEX-132 makes a write reach the System it names and offers there what the visitor's rights let through, HEX-134 the agent's lines. Nobody holds *write* on another's System in the app yet, no program writing a Grant before HEX-128 and HEX-131, so nothing a user can reach today is held back. A first draft gated each line by the rights on its Tile, its holder and its landing parent (cubic's first local review on #144 kept it); the second review found that a copy of Mapping's `allowed`, already looser (a move or a delete needs *write* on all it carries, and a move must not widen), so the gate went for the two modes: when HEX-132 offers writes on a visit, the client should ask a pure check of Mapping's door over `Seen`'s rights, as it asks `decide`, rather than a table of its own. What a visitor sees at all stays Mapping's (`Seen`).

**Following a visit.** No Version is a visitor's to poll (DEC-3), so the visited System is read again whenever the tab regains focus, and, as the Account's, once a write to the System settles; the owner's Version moving is HEX-132's to follow. A Message sent during a visit goes from the Account's own Root, where its Turn starts, as during the tutorial. The gestures are recorded in the Account's timeline as at home; `conversationDay` names their Tiles through Mapping's `titlesAcross`, the System holding each read as the Account may see it, one lookup for the ids its own System holds no Tile of (`starsHolding`) and one read of each other System named, and the chat names a gesture not yet recorded by the Titles of every System visited since the page opened. A Tile the chat names is centered on the System holding it, the one visited or the Account's, or visited by its link otherwise, a deleted one included, which then shows "Nothing to see here".

**Copy link** copies `/t/<id>` now (`visitLinkOf`, over `tilePage`, which sits beside `tileOfLink` in `api/mapping/files/download.ts`), on every System: the link home centered on a Tile, which an export still writes for a Reference it leaves out and an import reads back (`tileLink`), would have centered a visitor's own System. An import reads both back (`tileOfLink`), so a copied link pasted into a file still lands as a Reference (cubic's second local review on #144).
