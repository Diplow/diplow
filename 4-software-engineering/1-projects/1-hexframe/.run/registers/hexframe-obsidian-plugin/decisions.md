# Decisions

### DEC-1 `build` writes into `dist/` until HEX-30

HEX-28, [#36](https://github.com/Diplow/diplow/pull/36). CI already builds the plugin once `3-obsidian-plugin/package.json` exists, and fails when `.obsidian/plugins/hexframe/` then differs from what is committed. Committing the build is HEX-30's work, so the scaffold's `build` writes into the package's own `dist/`, ignored by git, and leaves that folder alone: CI stays green with nothing committed there. HEX-30 points `build` at `.obsidian/plugins/hexframe/` and drops `dist/`. `dev` already writes into a vault's plugin folder, the worktree's own unless `HEXFRAME_VAULT` names another vault.

### DEC-2 The `obsidian` typings are 1.13.1, not 1.14.x

HEX-28, [#36](https://github.com/Diplow/diplow/pull/36). The ticket asked for typings pinned to the current app, which it took for 1.14.x. The app installed here runs 1.13.7, and the newest `obsidian` package on npm is 1.13.1, so the typings are pinned to exactly that, and `minAppVersion` follows them: the plugin types no API the app lacks.

### DEC-3 `styles.css` is a plain file copied beside `main.js`, and `build` owns its folder

HEX-30. The ticket asks `build` for `main.js`, `manifest.json` and `styles.css`, and the plugin has no styles yet. `styles.css` sits beside `manifest.json` in the package, holding one comment, and every build copies it as it is, the way it copies the manifest. A ticket that brings styles writes them there, or switches to a CSS file esbuild bundles, as long as the output keeps the name `styles.css`. DEC-1 is done: `build` writes into the repo's `.obsidian/plugins/hexframe/` and `dist/` is gone. Since `dev` writes into that same folder by default, a production build also removes the `.hotreload` a dev build leaves there, so after `pnpm build` the folder holds exactly what is committed, and CI's build-and-compare step fails on a committed `.hotreload`.

### DEC-4 The view state at depth 1: a center and the outer ring's kind, decoded by hand

HEX-33. The ticket asks for the file's JSON to hold the center and the expansions, and HEX-35 owns the double expansion. So `expansions` holds only `outer` for now, the kind of the ring around the center (`children`, `branches`, `leaves`), defaulting to Children, or Branches when the folder offers no Children ring; HEX-35 adds `inner` and the Branches' own beside it. The decoder is a hand-written function in `view-state.ts` rather than Effect Schema: the plugin bundles no runtime dependency, and two fields don't justify one. A malformed field falls back on its own, so one typo doesn't reset the center.

### DEC-5 The shape is written in erasable syntax, and the bundle lowers template literals

HEX-33. The plugin's `tsc` type-checks the shape it imports, under `erasableSyntaxOnly`, which refuses the parameter properties of `exclusions.ts`'s `Cursor`: they became plain fields, with no change in behavior. And the shape joins lines with template literals holding `\n`, which esbuild's minifier writes as raw line breaks, so the production build no longer fit on the two lines `bundle.test.ts` takes as the mark of a minified build: the bundle now lowers template literals to string concatenation (`supported: { 'template-literal': false }`), which keeps each `\n` an escape.

### DEC-6 `diplow.hexframe` is empty, and the root STACK doesn't list it yet

HEX-33. The vault's entry is an empty `diplow.hexframe` at the root: empty means the defaults, the root's Branches. It is a Leaf of the root, beside `STACK.md` and `cubic.yaml`. The root `STACK.md`'s table of root-level pieces should name it, but the run may not edit that file: a line for it there is left to me.

### DEC-7 The plugin reads a Frame with its own copy of claude-mod's read, for now

HEX-33, [#39](https://github.com/Diplow/diplow/pull/39). `vault/frame.ts`'s `readFrame` follows the steps of claude-mod's `loadFrame` (exclusions first, then the sort, then one Tile per seated member, an overflowing ring left as names), over a `Disk` port instead of `$.fs`. It adds one rule claude-mod lacks: every read must lie within the vault's real path, since Obsidian's index lists a symlinked folder as a folder. Moving one `readFrame` over a port into the shape would stretch the shape's rule that a medium does the file system calls, and it would change claude-mod's pane, so this ticket keeps the copy and leaves that call to me. cubic raised it in every review round of #39.


### DEC-8 The clicks the ticket left open, and what a click may open

HEX-34. The ticket's click rules leave four cases open, settled here so they read the same everywhere:

- **The center goes up and shows the note there.** Going up is centering on the folder holding the center, so it shows that folder's note, as centering on a Branch does: the pane follows the view. At the vault root there is nowhere to go up to, and the click shows the root's own note.
- **A Leaf that isn't Markdown goes to the default app, shift held or not.** The paired pane is for notes, and Obsidian opens most files that aren't Markdown in no view of its own.
- **The paired pane is split off the view's own leaf** with `createLeafBySplit(this.leaf, 'vertical')`, not `getLeaf('split', 'vertical')`, which splits whichever leaf is active: the two match when the click comes from the view, and the first can't split another pane by mistake. The note opens with `active: false`, so the view keeps the focus for the next click.
- **What a click opens is held to the vault, as what the view reads is.** A note or a file whose real path leaves the vault, through a symlinked folder, opens nothing, and a folder whose real path does is not centered on; a notice says why. Obsidian types no "Open in default app", so the view calls the app's own `openWithDefaultApp`, checked to exist, and says so in a notice when it is missing. The system runs some files rather than opening them, and follows a shortcut wherever it points, out of the vault included, so it is handed only a document from a short list of extensions (`documents` in `vault/frame.ts`: PDFs, images, sounds, videos and plain text files, not office files, whose apps run the macros, links and formulas they carry), checked on the name written and on the real path, and a file with no extension never. Anything else is refused with a notice. A list of what to refuse can't be complete, so the list says what to allow; the cost is that a `.zip`, a `.html`, an office or a source file opens from the hexframe in nothing. cubic raised it in all three review rounds of HEX-34. One race is left, and accepted: the check and the open are two steps, since `openFile` and `openWithDefaultApp` open by the vault path again, so a symlink swapped in between them would be followed. Neither API takes a checked handle, the way `disk.ts` reads one, and winning that race takes someone writing in the vault at the instant of the click, who could put the file there in the first place.

### DEC-9 The shape lays out opened hexes, and the plugin keeps which ones

HEX-35. HEX-42 had taken the depth and `FrameView.expanded` out of the shape's layout until a medium drew them (claude-mod's DEC-6). They come back in another form: no depth number, since the view's own state says how deep it goes. A `FrameView` gains `inner`, its Tile's hex opened into a ring of another kind, and `expanded`, members opened as Frames of their own; a `CollapsedView`, a center with no ring around it, fills the view, opened into `inner` when it keeps one. A hex the view opens comes first, marked `opened`, and the Frame it holds follows, a third of its size short of a margin of 0.08 of its radius, the app's, so the Frame stays inside the hex a renderer draws at 0.93 of the layout's radius. Each placement now carries its `radius` and its `generation` (0 the center, 1 its members, 2 theirs), which the plugin reads to size words and to know the Branches around the center. The hub of an opened member is that member again, at the smaller size, so a click on it does what a click on the member did. claude-mod opens nothing, so its seven hexes come out as before, with the two new fields at their depth-1 values; no `kind` was added, so its renderers needed no change.

### DEC-10 The expansions in the file, and the temporary switch

HEX-35. The ticket leaves the file's shape and the switch open; settled so:

- **`expansions` holds `outer`, `inner` and `branches`.** A peeled ring is `null`, since a missing field already means its default (HEX-33's files hold `outer` alone, and still read the same, Context inside). A missing `outer` takes the one that sits beside `inner`: Branches beside Leaves, Children beside Context, nothing beside nothing. A pair no view shows keeps the outer ring, with Context inside, and a line says so. The pairs are a TypeScript union (`CenterExpansion`) built only through `centerExpansion`, the one function that says which pairs exist, so an outer ring with no inner one can't be written.
- **A Branch's expansion is keyed by its direction, and belongs to the center.** Centering elsewhere, switching or peeling the outer ring closes them all, so the file never keeps an expansion no hex shows. A path key would survive a renumbering, but it would need following on every rename, and a direction is what the user clicked.
- **What the folder lacks is resolved when drawing, not written.** A file asking for Leaves around a folder that offers Children shows Children, and keeps asking: the same file still opens Leaves on a folder that has them. The switches start from what is shown, an opened Branch's included, and a switch that changes nothing writes nothing, so the file keeps asking.
- **A peeled center fills the view, its inner ring inside its own hex**, rather than drawing the inner ring at full size like an outer one: what the eye sees then says which ring is left.
- **The temporary switch is four header buttons and alt-click.** Collapse, expand, switch the ring around the center, switch the ring inside it, each a `view.addAction` on the view's header, and an alt-click on a Branch around the center cycles it through the kinds its folder offers, then closes it. HEX-37's menu and shortcuts replace them.
- **The drawing was looked at in a browser, not in Obsidian.** The run can't drive the Obsidian app. Every layout (the default, Branches and Leaves with two Branches opened, Leaves and Context, Children and Context with a Branch opened, a peeled center, a collapsed one) was rendered by the real `drawView` into a page holding `styles.css` and Obsidian's default theme variables, light and dark, and checked there. A look in Obsidian is left to whoever merges the project branch.

### DEC-11 The paired pane is followed through `file-open` on the active pane, its own opens skipped by path

HEX-36. The ticket names `file-open` and `active-leaf-change` and leaves the pick open. The view listens to `file-open` alone: Obsidian sends it whenever the active pane's file changes, so it already covers a link followed in the paired pane and a return to that pane, and `active-leaf-change` would only send the same opens twice. An open counts as the paired pane's when the active `FileView` is that pane's and shows the file opened, since Obsidian also sends `file-open` for a note embedded in the active one: the view opens its notes with `active: false`, so its own opens never pass that test, and an open in any other pane never does either.

Ignoring the view's own opens is done by path, not by a flag around `openFile`: Obsidian doesn't say whether, or when, an inactive open sends `file-open`, so a flag could be left set and swallow the user's next move. The view keeps the note of the paired pane it dealt with last, one it showed there itself or one it followed or refused to follow, and skips it when it opens again: coming back to the pane after a shift-click doesn't center on a hex the user chose not to center on, and a refused folder's notice shows once, not on every return. Every other open in the paired pane becomes that note, so going back to an older one later, by the back button, follows like any other open. The rule lives in `followed`, which returns that note beside the folder to move onto, so the test covers it. A note of the folder already in the center moves nothing and writes nothing, since recentering resets the expansions. A followed open is a move like a click: it counts in the same sequence, so a slower click or follow that a later one overtook is dropped, and it is held to the vault by the same check, with the same notice when refused.

The run can't drive the Obsidian app, so the follow was not looked at in it: the filter is tested in `follow.test.ts`, and a look in Obsidian (a wikilink to another folder's `CLAUDE.md` followed in the paired pane, then a shift-click, then a return to the pane) is left to whoever merges the project branch.

### DEC-12 The menu's items, what the ticket left open

HEX-37. The ticket gives the items, their keys and the hexes they act on, and leaves these open:

- **"Exclude from the six" (`E`) and "Hexframe settings" (`,`) wait for HEX-39.** HEX-39's own steps write `.hexframe/exclusions.yaml` through the adapter, keep the globs written by hand, and wire "the `,` and `E` commands" to its panel. An item with nothing to carry it out would be dead code, and a second writer of that file would have to agree with HEX-39's on every glob, so the menu lists nine items and HEX-39 adds those two rows to `items` in `menu.ts`, with their handlers.
- **Preview is offered on every hex but a Leaf that isn't Markdown.** The paired pane is for notes (DEC-8), and that Leaf has "Open in default app", which a shift-click on it does already: listing both would show one action twice.
- **"Expand as" on the center opens the next ring, and on an open center switches the ring that can take the kind, the inner one first.** A collapsed center opens its inner ring, Leaves or Context; a peeled one its outer ring around the inner one, or switches the inner ring when the kind only sits inside (Context beside Leaves). With both rings open, Leaves on Branches and Context go inside, which keeps the ring around as it is, and switching the outer ring closes the Branches opened in it, as switching did before. An outer ring with no inner one is a pair no view shows (DEC-10), so a collapsed center lists no Children or Branches, and the key does nothing.
- **The kinds a closed Branch offers are read as the view draws.** A command's `checkCallback` answers at once, so the menu and the keys can't wait for a read to know whether a Branch offers Children. Each drawing reads the listing of every closed Branch around the center (`readKinds` in `vault/frame.ts`: its exclusions, then the sort, no Tile), held to the same check as a center; an opened one gives its Frame's. A Branch the view may not open, or can't read, lists no "Expand as".
- **The focus is the path of a Tile, kept by the view, not in the file.** The ticket puts it in the view state: it is the view's, in memory, beside the drawing, and the file keeps what the app keeps in its URL, which a focus is not. Every hex holding a Tile, the opened ones aside, holds another one, so a path names one hex and survives a drawing; a focus whose hex is gone goes back to the center, and the center is focused when nothing else is. `1` to `6` move within the ring the focused hex sits in (an opened Branch is its own ring's neighbor), from the center the ring around it, or inside it once peeled; Tab steps through every hex in drawing order, an opened Branch's members right after it.
- **Item keys are commands, Tab and the digits are the view's.** Each item is a command with a bare key as its default hotkey. Obsidian's hotkey manager (1.13.7, read in its app bundle) consumes a key only when the command it is bound to runs, and a `checkCallback` that answers false doesn't run, so outside a hexframe view, or on a hex where the item doesn't apply, the key goes on to the editor or whatever else takes it. A command also refuses while the user types in a field anywhere, the view's title or a popover's editor, while the view stays the active one, so typing stays typing; a modal is left out, since Obsidian runs no hotkey there and the command palette keeps the focus while it lists the items. Tab, shift-Tab and the digits are registered on the view's own `Scope`, active while it has the focus, and are not rebindable: they move the focus rather than act.
- **The menu is Obsidian's own, never the system's.** A native menu shows no key beside a title, so the menu sets `setUseNativeMenu(false)`. The key it shows is the hotkey manager's `printHotkeyForCommand`, which prints the binding set in Settings → Hotkeys, or else the default, as Obsidian prints keys everywhere; its API doesn't type it, so the view checks it exists and shows no key otherwise.
- **The temporary switch is gone.** The four header buttons and alt-click (DEC-10) are removed, with `expand`, `switchOuter`, `switchInner` and `switchBranch` and their tests: "Expand as", "Collapse" and `openBranch`/`closeBranch` replace them.
- **Not looked at in Obsidian.** The run can't drive the Obsidian app: which items apply to which hex is tested in `menu.test.ts`, and the focus in `focus.test.ts`. A look in Obsidian (a right click on the center and on a Branch, Tab and a digit, then `L` and `X`, and a key rebound in Settings → Hotkeys showing in the menu) is left to whoever merges the project branch.

### DEC-13 An overflowing ring as a list, what the ticket left open

HEX-38. The ticket gives the rule (only the overflowing Frame becomes a list, inside its hex or behind a hex saying how many, the whole view when it is the center's outer ring, names acting as hexes) and asks for it to be tried. Settled so:

- **The shape's layout places the list, the plugin draws it.** A hex opened into a ring that overflows comes out of `layoutView` with `list`, the ring's kind and candidates, and nothing placed inside it, as claude-mod's DEC-4 left for this ticket. It is not marked `opened`: no hub holds its Tile, so the hex itself takes the clicks and the focus. A view whose own ring overflows comes out as its center alone, its `list` marked `fillsView`, so the shape says in both cases that a ring is a list and the plugin only looks it up. claude-mod opens no hex, and checks its own ring for overflow before it lays anything out, so neither placement reaches it.
- **A name holds a Tile made from it**, its path in the ring's folder and its title the name as an exclusion writes it, folders with a trailing `/`. A list reads no file (DEC-4 of claude-mod), so a name has no preview, and it is a `ListItem` beside the hexes rather than a hex: it has no direction, so "Expand as" and "Collapse" never apply to it, and the click rules and the other items apply unchanged.
- **Whether a list fits is set by the words**: one name per line under the hex's title, in the band its words already use and a height of 1.1 times its radius, at the preview's size. That gives six names in a hex of the first scale, the center's or an opened Branch's, and ten in a collapsed center, the only two sizes a list can take. The text styles moved out of `draw.ts` into `text.ts` for it, so `fitsIn` in `list.ts` decides it for the drawing and for the focus alike, and the focus is tested with real sizes.
- **"Too many to draw" opens the list to fill the view**, and so does "Show the list" (`S`), a menu item and command on any hex holding a list but the one whose list already fills the view, so the keyboard reaches names that don't fit; a button and `Escape` go back to the hexes. The list is a Menu nowhere, since a shift-click and a right click on a name must work as on a hex. The opened list is kept in the view, not in the file, like the focus (DEC-12), by the path of its hex's Tile and the center it was opened around: it closes when the view centers elsewhere, even onto a folder whose hex has the same path, or when the hex no longer holds a list.
- **"Choose six" is a disabled button** on a list filling the view, its tooltip saying it comes with the settings. HEX-39 writes the exclusions that pick the six, so it wires the button; a hex holding a list has no room for one.
- **The line under the drawing stays**, reworded: the ring shows as a list, and it names at most three of the names left without a direction, then how many more, as claude-mod's hint does. It names the kind as the list does, "7 Leaves", "2 Context folders".
- **Tried on the real vault, in a browser, not in Obsidian.** The run can't drive the Obsidian app, so the real `drawView` and `drawFullList` drew Frames read from this worktree into a page holding `styles.css` and Obsidian's default theme variables, light and dark. `1-app/` has seven Leaves once its dot files and `CLAUDE.md` are set aside (the ticket counted fourteen files), so its Leaves overflow: inside the center beside its Branches they don't fit and read "7 Leaves, too many to draw", collapsed they fit, and as the outer ring the whole view is their list. `3-obsidian-plugin/src/` has eighteen Leaves, which a collapsed center doesn't fit either. The vault root's Context doesn't overflow: with `.git` and `.hexframe` left out everywhere, git holds five dot folders there (`.claude`, `.conductor`, `.github`, `.obsidian`, `.skills`), and this Conductor worktree adds its untracked `.context`, six. What read badly, and changed: a Branch's list read as its preview, so names take the text's color, and the line under the drawing said "2 context". What still reads badly, left to whoever merges the project branch: a collapsed center holds ten names in a hex that could hold two columns, so eighteen leave it nearly empty around one line; and that line is small at the first scale. A look in Obsidian (`1-app/` with its Leaves inside and around, a click, a shift-click and a right click on a name, the line that opens a list, then `Escape`) is left to that merge too.

### DEC-14 The settings panel, what the ticket left open

HEX-39. The ticket gives the panel (every candidate of each kind, a checkbox each, a live count against six, saved to the folder's `.hexframe/exclusions.yaml`), the ways in (a gear, "Choose six", `,`) and `E`, and asks that hand-written globs survive. Settled so:

- **Which folder.** The gear and "Hexframe settings" (`,`) open the center's folder, as the ticket says, whichever hex has the focus, so `,` applies on every hex and name. "Choose six" opens the folder whose ring the list is, which is the center's for its own rings and an opened Branch's for that Branch's: the six to choose are that folder's.
- **"Exclude from the six" (`E`) leaves a hex out of the folder holding it**, on every hex but the center and on every name of a list: a member of the center's rings goes into the center's file, an opened Branch's own member into that Branch's. The center is never offered: left out of its parent, the view would refuse to center on it (`refusal`) and fall back to the file's own folder. It writes at once, with a notice naming the file, and unticking it in the settings undoes it.
- **An item holding `*` or `?` is a glob**, even one written as a candidate's own name, since it matches more than that name, and the file has no escape for either. A candidate whose name holds one can't be left out alone: its checkbox is disabled while nothing leaves it out, and `E` doesn't apply to it. cubic raised it on #45.
- **A tick writes the name, an untick removes only names.** Ticking a candidate adds its pattern, a folder's with its trailing `/`, as a list shows it (`patternOf`). Unticking removes every item that names it exactly, `src` or `src/`. A candidate a glob leaves out stays ticked and can't be unticked, and the row names the glob: removing the glob would bring back everything else it matches. The items that name no candidate, globs and names of what is gone, are listed under the kinds as kept.
- **The writer stays in the plugin, not the shape.** cubic's domain-design agent asked twice on #45 to move `withChange` beside `parseExclusions`. The shape holds what every medium reads, and claude-mod writes nothing: the one medium that writes keeps the write until a second one needs it, as DEC-7 kept `readFrame`. Every line it keeps or drops is read by the shape's parser, and what it would write is parsed again before it is.
- **The file is edited line by line.** Only the lines of the items removed go, and the items added follow the last item in the list's own indent; comments, the blank lines between lines, globs, their order and the file's line ending stay as written, and trailing blank lines are dropped for one final line ending. A flow list (`exclude: [a, b]`) becomes a block list, one item a line, its comment kept after the key, since an edit inside the brackets would have to rewrite the line anyway. An item is written bare when it holds only letters, digits, `.`, `_`, `-` and a trailing `/` and doesn't start with `-`, else double-quoted, so a glob's `*` or a name's ` #` reads back as written; the round trip goes through the shape's own parser, and what would be written is parsed again and refused unless it reads back as the change. A name holding a line break or another control character can't be written at all, since the parser has no escape for one: it is refused with a notice. A file the shape can't parse is never written over: the panel says why and offers only Close, and `E` says so in a notice.
- **The count is the shape's.** Each kind counts its candidates left in, and its ring is sorted with the ticks as `sortEntries` sorts it, so a count of six or fewer whose ring still overflows, two names on one number, says so. A line says when Branches and Leaves, six or fewer in all, draw together as Children.
- **Where the write lands is checked as a read is.** `readSettings` refuses a folder the view may not center on (`refusal`), a `.hexframe` that isn't a folder at the folder's own real path plus `/.hexframe`, and an `exclusions.yaml` the shape wouldn't read there (`unreadable`, which takes no symlink for that file, even one inside the vault), so a write never speaks for another folder nor leaves the vault. Save reads the file again just before writing and applies the ticks as a change, items added and removed, so a line written meanwhile elsewhere stays, and the saves run one after the other through one `saverOf` per vault, so a second `E` pressed while the first writes doesn't write over its line. The shape now exports its `settingsFolder` and `isGlob`, so the plugin names `.hexframe` and tells a glob as the shape does. The write is the one place the plugin leaves the ticket's letter: it asks for `vault.adapter.write`, but the adapter writes by path and follows symlinks, and Node's `stat`, which `readSettings` checks with, sees a dangling symlink as nothing, so a dangling `exclusions.yaml` would have been written through, out of the vault (cubic's local review, round 2 on #45). So `writerOf` in `disk.ts` writes through Node, as `disk.ts` already reads: `.hexframe/` made with `mkdir`, which refuses a name already there, a dangling symlink included, then the file opened once with `O_NOFOLLOW` and `O_NONBLOCK`, checked to be a regular file on that handle, and only then emptied and written. It sits behind a `Write` port, so `saveSettings` is tested with the in-memory vault. One race is left, and accepted, as in DEC-8: Node has no `openat`, so the no-follow open guards the file, not the `.hexframe/` above it, and a symlink swapped in for that folder between the check and the write would be followed, by someone already writing in the vault at that instant. cubic's security agent raised that race on #45 too, offering a no-follow write or the risk named and accepted: both are done.
- **The gear is Obsidian's `settings` icon**, in a `clickable-icon` button, rather than the ⚙️ emoji, so it follows the theme as the header's buttons do. It is drawn once a center is read. The checkboxes are native ones inside labels, as the ticket names them, rather than Obsidian's toggles, so a long list of names stays dense.
- **Not looked at in Obsidian.** The run can't drive the app. The panel's model ran on `1-app/`'s real listing in this worktree: 4 Branches, 7 Leaves ("7 of 6, 1 too many: they show as a list") and 1 Context folder, `.output`, a build left untracked here; ticking `vitest.config.ts` brings the Leaves to 6 of 6, and the file it writes is `exclude:` and that one line. A look in Obsidian (the gear and `,` on `1-app/`, ticks until the Leaves fit, Save and the hexes drawn again, `E` on a Leaf, then unticking it) is left to whoever merges the project branch.
- **The pull request goes into the project branch.** The ticket's last step says main; this run lands every unit on `project/obsidian-plugin`, which a human merges into main.
