# Decisions

### DEC-1 Mapping declares its rows in `entities/rows.ts`, and the repository answers them flat

HEX-63, [#72](https://github.com/Diplow/diplow/pull/72). The ticket asks for "Mapping's own row shapes, which the repository's `TileRow` satisfies structurally (`contentWith` moves in)". `entities/rows.ts` declares `Row`, `RowWith`, `FieldsAsked`, `StoredConfig` and the kept parts, and Mapping's projection, `contentWith` and `withContent`, which `showing`, Help's reads and `mapping.ts`'s reads use. The tiles repository projected its rows the same way, nesting the content columns asked, and a repository imports no domain, so the projection would have been written twice; cubic's local review on #72 asked for one. The repository now answers a read from one Tile flat, `TileRowWith` a row selecting only the content columns asked, and Mapping nests it with its own `withContent`, as it does Help's notes. `TileRow` and the repository's `ColumnsAsked` satisfy Mapping's shapes as they stand: the compiler checks it wherever `mapping.ts` hands repository rows to a reading in `entities/`. `rows.ts` stays in the door's index, as the ticket puts Mapping's row shapes behind `entities/index.ts`: pure, the front may read them, and Mapping's other folders import them from there. `TileConfigColumn` stays the schema's, and `Naming` is now typed from `StoredConfig`, its twin on Mapping's side.

### DEC-2 `operations/` opens with `Placement`, so its door is no dead file

HEX-63, [#72](https://github.com/Diplow/diplow/pull/72). The ticket asks that `operations/` exist with its `index.ts`, filled by HEX-64. An index that exports nothing is a file nobody imports, which knip refuses, and an ignore would weaken that gate. So `operations/placement.ts` takes `Placement`, where an operation puts a Tile or a Reference, a slot under a parent Tile, which `mapping.ts` declared, and `ReferenceSlot`, a Context slot by the Tile that holds it: the argument `CreateTile`, `MoveTile`, `CreateReference` and `DeleteReference` will each carry, rather than a value object of the System. `mapping.ts`, `landing/` and `api/mapping/programs.ts` import them from the door, the last in place of `Parameters<typeof Mapping.moveTile>[2]` and `Parameters<typeof Mapping.deleteReference>[1]`. HEX-64's Operations carry it, or replace it.

### DEC-3 Mapping regroups: `kept/` and `leaves/` move under `entities/`, their tests over PGlite to Mapping's root

HEX-63, [#72](https://github.com/Diplow/diplow/pull/72). `domains/mapping/` held six files and five folders; `entities/` and `operations/` take two folders, and `tile.ts`, `system.ts` and `system.test.ts` move into `entities/` with `kept/` and `leaves/`, leaving the root `mapping.ts`, `errors.ts` and `mapping.test.ts`, and the folders `entities/`, `operations/`, `files/`, `landing/` and `help/`. `files/`, `landing/` and `help/` stay concept folders: `help/` reads the help repository and `landing/` writes through the tiles one, so neither may sit behind the door, and `files/` imports `yaml` and the shape. Nothing under `entities/` imports a repository, its tests included, so `kept.test.ts` and `leaves.test.ts` split: the checks on values and rows made by hand stay beside their modules, and the cases over PGlite, which run the application service, move to `domains/mapping/kept.test.ts` and `leaves.test.ts`. `entities/` gets a `CLAUDE.md`, which takes the rows Mapping's own tables gave `tile.ts`, `system.ts`, `kept/` and `leaves/`. Mapping's other folders import `entities/` through its `index.ts`, as the API layer and the front do, so one list says what the door offers.

### DEC-4 The front and the API take entity values from the door; a concept folder's still come through the API layer

HEX-63, [#72](https://github.com/Diplow/diplow/pull/72). `Direction`, `ContextDirection` and `Slot` become Effect Schemas in `entities/tile.ts`, each with its type, so the server functions decode a slot by Mapping's own schema and the System page's URL by the same one; `api/mapping/mapping.ts` no longer declares them. The front imports `Slot`, `directions`, `SystemTile`, `holdsNothing`, `isEmptySystem` and `ImportRefused`'s type from the door, and `isLeafSlot` and `isContextSlot`, which `features/system/tree.ts` had written on its own until cubic's local review on #72 found them there: `api/mapping/rules.ts` and the `ReturnType` stand-in in `front/client/mapping/queries.ts` are gone, and `features/system/tree.ts` walks a System by Mapping's `directions` rather than the canvas's. `mapping.ts` re-exports no entity any more (the MCP's tool table takes `fields`, `depths`, `directions` and `previewLimit` from the door), only Help's `HelpId`, `helpRoot` and `helpSystem`, which live in a concept folder. The ticket says the API's re-exports of domain values go; those of `files/` and `landing/` stay (`api/mapping/files/download.ts`'s `isVerbatim`, `files/upload.ts`'s reading rules and archive checks), since a concept folder is past the door and the browser still reaches it, as it reaches the zip repository's plain functions, through the API layer.

### DEC-5 The door's two rules are proved on a small app written to a temporary folder

HEX-63, [#72](https://github.com/Diplow/diplow/pull/72). The custom rules in `scripts/lint.test.ts` were proved by testing their regular expressions, but a reachability rule fires on a path through the graph, which no pattern test shows. The door's are proved by cruising: the test writes a small app, a domain with its door, its service and a concept folder, another domain, a repository and a page, cruises it with the app's own rules (`dependency-cruiser`'s `cruise`, its `baseDir` the temporary folder) and checks that the app as written breaks nothing, that the page importing past the door breaks `no-front-past-a-domains-door`, and that the door reaching a repository by a type-only import, the service, a concept folder, another domain or `node:fs`, a file away, breaks `no-door-reaching-past-the-pure-model`. `effect` resolves to a bare name here, as it does under `src/` once cruised, so the rule allows `effect` bare or in `node_modules/`.

### DEC-6 STACK.md still says the door is to come, for the phase close to change

HEX-63, [#72](https://github.com/Diplow/diplow/pull/72). `STACK.md` ("Domains") says that until this project lands, the front reaches a domain only through the API layer and events reach the bus as they are published. The door and its two rules are now in place, which cubic's local review on #72 found the sentence contradicting. `STACK.md` is frozen for this run, so it stays as written; the app's, the domains' and the front's `CLAUDE.md` files say what holds now, and this entry is the line for the phase-close ticket, which lists for me what the project changes in `STACK.md`: the door and its lint are built, the Decider and the held events are what remains.

### DEC-7 The service runs an Operation by one function per tag, each taking its class

HEX-64. The ticket leaves the call open: `run(accountId, operation)` or one function per tag. `mapping.ts` keeps one function per Operation, named by it (`moveTile(accountId, operation: MoveTile)`), because their answers differ: a create and an edit answer the Tile, the others nothing, and a `run` over the union would widen every server function's and MCP write's answer to a union its caller narrows again. `decide`, in HEX-66, is where one function meets the whole union. `createTile` takes what an import keeps (a Name, a Tile config, Frontmatter) as a third argument, since only an import sets them and they are no part of the Operation. The tests that prove Mapping refuses Help's ids itself build their Operations with `disableChecks`, as a caller whose schema let a Help id through would; every other test builds them through their checks.

### DEC-8 A server function and an MCP write take the Operation's fields, without its tag; a create without its `id` until Mapping honours it

HEX-64. The bounds the server functions declared (a UUID per id, a Title, a Preview and a Body each within its bound) move into `operations/operation.ts`, with `TileId`, so each Operation refuses what the server functions refused, and `api/mapping/mapping.ts` derives each input from its Operation's `fields` with the `_tag` left out (`Struct.omit`). The tag stays out of the wire because the function's name already says it, and because an MCP write lists its input to agents: a `_tag` property would change every write's schema, which the ticket keeps as it was. A program makes the Operation from the decoded fields with `new`, which checks them again, cheaply, so nothing past its schema reaches the service. `NewTile`, and so `create_tile`, leaves out the `id` a `CreateTile` declares: until HEX-68 honours it, a caller sending one would get a Tile under another id with no word of it. `mcp.test.ts` pins every tool as an agent lists it in a snapshot written before the change, which still matches after it.

### DEC-9 An Operation's name is its tag in camelCase; the timeline names an operation by its tag

HEX-64. `OperationName`, `Uncapitalize<Operation['_tag']>`, is the one name of an Operation outside its tag: the service's function that runs it, its server function, the MCP write's `operation`, the scope the message table narrows a refusal by and the client's write hooks scope by, all `swapTiles`. The message table's `scope` is typed by it, beside `importTiles` and `submitDevTitle`, the two other calls it narrows. The Conversation's timeline names an operation by its tag rather than four verbs of its own, so it gains a swap and the Reference's create and delete, each with its sentence in English and French. `ReferenceSlot`, the interface DEC-2 put in `operations/`, goes: `CreateReference` and `DeleteReference` carry it. `Placement` stays, for `freeSlot` and the import's place.

### DEC-10 The flat System holds its Root apart and says `owned`; `useSystem` answers it with its tree

HEX-65. The ticket asks for the System as a flat entity: every Tile by id with its parent, its slot, its content and what it keeps, its target when it is a Reference, the Root, and whether an Account owns it. `System` (`entities/system.ts`) is `{ root, tiles, owned }`: the Root apart, since it alone has no parent nor slot, so `PlacedTile` and `PlacedReference` carry a `parent` and a `slot` that are never null and `systemOf` is total, a `SystemTile` and never `undefined`; `tiles` every Tile and Reference below it, keyed by id in a plain record, which crosses the wire as it is. A Reference keeps its own id, has no content, and stands only in a Context slot (`slot: ContextDirection`): `systemFrom` leaves out a Reference row elsewhere, and a row in no slot, as the tree left them out before. Ownership is `owned: boolean`, what `decide` needs to refuse `HelpReadOnly` (HEX-66), rather than the owner's id, which no reader needs yet; sharing (MR-12) decides whether an owner's id joins it. `systemOf` takes the flat System, never rows, and resolves a Reference to the Root too, as it did. `helpSystem` builds Help's flat System, owned by none, then its tree, so `/help` draws what it drew. On the client, `useSystem` keeps the query's data what the server said, the flat System, and answers `{ system, root }` through TanStack Query's `select`, a module-level function, so the tree is built once per answer and the overlay of HEX-70 can fold pending Operations over the flat `system` before building its tree. The tests that read a System over PGlite take its tree through a `tree` helper beside them, `Effect.map(Mapping.system(accountId), systemOf)`, since what they check is drawn on a tree; the flat read is pinned by `api/mapping/mapping.test.ts` and `entities/system.test.ts`.

### DEC-11 `decide` is typed per Operation and given what a create makes; the service runs every Operation through one `operate`, and Help is a System no Account owns

HEX-66. `decide(system, operation)` answers a `Result`: the events, or a refusal. Its overloads type each Operation's refusals apart (`Refusals` in `operations/decider/decide.ts`), so a server function's and an MCP write's error types stay the ones the Operation can get, which `api/mapping/mapping.test.ts` and the MCP's refusal tables pin; one union would have asked every caller to handle `RootFixed` on an edit. A create takes a third argument, `Made`: the id of what it makes, which the tiles repository now makes before the write (`Tiles.newId`, then `Writes.insert` under it), and, for a Tile an import makes, what it keeps, already checked. Spreading it into the Operation was the other way, refused by `no-misused-spread` on a class instance, and an `id` field would have collided with an edit's or a move's own. So `NameInvalid` is never `decide`'s: `ToKeep`'s branded types take only a checked Name and config, and `named` and `configured` stay `Effect`s for an import's input, outside any Operation. The rules `decide` reads are `Result`s on the flat System: `checked`, `notLeaf`, `holdsNothingIfLeaf`, `onlyALeafIn`, and `freeSlot`, which moves to `operations/placement.ts`, where `landing/` asks it on a System built from the rows it locked; `rowAt` and `below` on rows give way to `tileAt`, `heldAt` and `below` on a System. The events are the ticket's seven: `TileCreated` carries the id, the place, the content and what it keeps; `TileEdited` only the fields given, and an edit giving none makes no event, as a move to where a Tile stands, a swap with itself and an empty slot's Reference delete make none; `TilesSwapped` names the two Tiles, their places being the System's. The service runs each Operation through one `operate`: the Root added if the Account has none, as a read adds it, the System locked and loaded flat, `decide`, one write per event, and the events with the System `evolve` leaves. The functions per Operation keep their answers, the Tile for a create and an edit, read from that System, nothing for the rest, because `mapping.test.ts` pins them unchanged (`toEqual` on an edit's Tile); so the events stop at `operate`, where HEX-69 publishes them. An Operation naming a Help id is decided on Help's flat System, owned by none (`flatHelp`), which `decide` refuses before any other rule, so `HelpReadOnly` reads the System and `isHelpId` stays in `help/` for the service. `decide`, `evolve` and their tests sit in `operations/decider/`, since `operations/` would have held eight files. On the client, `swapsWith` asks `decide` on the flat System, which `System.tsx` now takes beside the tree: a Tile above or below the moving one no longer offers a swap Mapping refuses; a Leaf and a Reference still offer none, a choice of the canvas (`hexframe-app-import-export/decisions.md#DEC-13`). The grow and shrink of `useCenteredTileState` already ask Mapping's `holdsNothing`, and stay. The import (`landing/`) is no Operation: it still lands through `changing` on the rows it locked, refuses Help by `isHelpId` before it, and writes its batch with no event behind it, so once HEX-69 publishes events an import publishes none. `STACK.md` names the Root's first read as the one write no event explains; the import is a second, which `STACK.md`, frozen for this run, leaves for the phase-close ticket to list, as `#DEC-6` does the door.

### DEC-12 A create and an edit are a form's writes; the System's queue holds the import too; `submitWrite` keeps the password beside the Key

HEX-67. `write(scope, call, { as, queue })` keys a mutation `[scope]`, puts its call in `meta.call` (`mutationMeta` on `Register`), and queues it under TanStack Query's mutation `scope`; the MutationCache's `onError` sends a failure to the channel of that call and names it by the key's first part, so a mutation that does not come from `write` is a `write` still. `useCreateTile` and `useEditTile` are `submit` writes whoever calls them, since a Tile form is their only caller and the ticket keeps their refusals on the form: an `Invalid` one no longer raises a toast, which a create or an edit made outside a form would then not show; the day one is, it takes `as` from its caller. The variables stay the Operation's fields without its tag, as the server functions take them (`#DEC-8`): the mutation's key, the Operation's name (`#DEC-9`), says the tag, so the overlay of HEX-70 reads an Operation from a mutation's key and variables without a second shape on the wire. The form sends through `submitMutation({ mutate: mutateAsync, onSaved })`, which takes no scope of its own, since the error names the one its call settled under, and shows the mutation's error, the one the QueryClient carried out already, on the fields an `Invalid` refusal names, or on the form for any other, so the submit does not count as done, as `submitWrite` did. The queue is `system`, and the import waits in it too, keyed `importTiles`: it is a write to the System, and a move made after it must not reach the server before it; it stays out of `write` because its function prunes and zips before it calls, and its refusal is its answer (`settleSubmit`), but takes its key, meta and queue from `writing`, the half of `write` that places a write, so a System write is placed one way. A test proves it waits behind a move. `submitWrite` stays for issuing a Key, as the ticket says, and for signing in and up, whose variables would put a password in the MutationCache; `/dev/errors`' title form moves to `submitMutation`, so the page provokes the path the Tile forms take. A test proves the queue: a write made while another is pending reaches its server function only once the first is refused.

### DEC-13 A create's id is its caller's when given; the write finds it taken by the table's key, and only a chosen id is refused for it

HEX-68. `CreateTile`'s `id`, given, is the new Tile's; absent, Mapping makes one (`Tiles.newId`), as it does every Reference's. Whether an id is taken is no rule of a System: a Tile of another Account's may hold it, and `decide` sees one System, so the rule cannot live in `decide` as the others do. `Writes.insert` adds the row with `ON CONFLICT (id) DO NOTHING` and answers `IdTaken`, a repository error, when it added nothing; any other constraint broken stays a defect. Mapping turns `IdTaken` into `TileIdTaken` (Conflict) when its caller chose the id, and into a defect when Mapping made it, through the `onTaken` its `operate` takes, so no other Operation's type gains the refusal. Reading the driver's unique-violation code was the other way, refused because PGlite and `pg` report it differently and the key's name would leak into the domain's concern. `createTile` has one signature, whose type lists `TileIdTaken`: TypeScript cannot follow an id's absence through `new CreateTile(...)`. cubic's local reviews on #77 weighed two signatures, first in the API layer with an `Exclude`, then in Mapping, against one; one won, for the smaller model. The MCP's write, which sends no id, says what it knows at its call: `Effect.catchTag('TileIdTaken', Effect.die)`, since Mapping made the id and a clash on it is a defect there too. So the MCP's `create_tile`, whose input leaves the id out (`NewTileOfAgent`), keeps its listed schema and its description (the snapshot in `mcp.test.ts` still matches) and is never taught a refusal it cannot meet. The server function's `NewTile` takes the id, a UUID by `TileId`. No replay: the same id sent twice is refused the second time, which the front's retry, if HEX-70 adds one, has to know. The tests: `api/mapping/mapping.test.ts`, over PGlite through `run`, a create under a chosen id kept, the same id again in the same System and another Account's both `TileIdTaken` with nothing written, and the schema; `agreement.test.ts`, a create under a chosen id decided as the client would decide it. `mapping.test.ts` holds 597 of its 600 lines, so the service's cases stay at the API layer, which runs the service on the same repositories.

### DEC-14 Who acted is read from the request when an event is published; `by` is `Session` or `Key(keyId)`; the bus waits for a commit through `AfterCommit`

HEX-69. `signedIn` answers `{ account, by }`, `by` a `Proof`: `{ _tag: 'Session' }` or `{ _tag: 'Key', keyId }`, the project's "`Session | Key(keyId)`" read as a tagged union whose Session carries nothing. Giving the Session an id too was the other way, refused: Better Auth's session row has one, but IAM's `Session` would gain a field every fixture and the client's `session` answer carry, for no reader yet; the Assistant's timeline needs to tell a user's write from an agent's, and which Key, which this gives. The Session wins when both proofs are present, as `signedIn` already took it first. The bus fills the actor itself when an event is published: it reads `CurrentSession` and `CurrentKey` from the request, if any (`Effect.serviceOption`), and asks IAM's `signedInBy`, the rule `signedIn` reads them by, so the actor is `Option<SignedIn>`, none for an event published outside a request or where nothing proves it (a sign-up's, later). Providing an `Actor` service from `programs.ts`'s `forAccount` was the other way, refused: every door and every program would have to remember it, where reading the request's proofs at the bus covers the server functions and the MCP writes at once, since both run the same programs. A reaction gets `(event, actor)`; `on`'s existing one-argument reactions still type. `transactional` collects what a program defers through `AfterCommit` (a `Context.Service` holding `(work) => Effect<void>`), runs it in order once the transaction has committed, in the same fiber, so the request's `WaitUntil` is still there for the subscribers' work, and drops it when the program fails or dies. One opened inside another hands its work to the outer one's commit instead. The bus checks for `AfterCommit` at each publish (`Effect.serviceOption`), so Mapping's type gains `Bus` and nothing of the hook: the domain publishes and never knows it waits. `serverBus` is provided its repositories in `run.ts` (`Layer.provideMerge`), `subscriptions` typed `Subscription<Auth | Database | Tiles | Zip>`; none is wired. The tests: `repositories/database/database.test.ts`, the hook's order, its drop on a failure and on a defect, the inner transaction's work waiting for the outer commit; `api/server/bus.test.ts`, an event held inside a transaction until it commits, dropped on a refusal and on a defect, and the envelope by each proof and by none; `api/mapping/events.test.ts`, the same edit by a Session and by a Key publishing the same `TileEdited` with each actor, a create's `TileCreated`, nothing for a refusal or an edit giving nothing; `domains/mapping/agreement.test.ts`, the events the service published equal to `decide`'s for every Operation. Mapping's other tests provide a bus that hears nothing. `mapping.test.ts` sat at 603 of its 600 lines once its change types took `Bus`, so its type checks name one `Change` alias.

### DEC-15 The overlay folds pending writes in `useSystem`, read from their key and variables by Mapping's schema; a refusal foreseen is a `Foreseen`; every write waits for the read after it

HEX-70. `useSystem` keeps the query's data what the server said and answers `{ data }`, the System the page shows and its tree, the server's with every pending mutation of the System's queue folded over it (`useMutationState`, `status: 'pending'`), in the MutationCache's order, its `mutationId`. `select: withTree` gives way to a `useMemo` over the data and the pending list, which `useMutationState` keeps referentially stable while nothing changes, so the tree is still built once per change. The fold is `front/client/mapping/overlay/overlay.ts`, pure, a folder of its own because `client/mapping/` held six files: a folder needs no regrouping, and its test, `overlay.test.ts`, keeps `queries.test.ts` under its 600 lines. A pending write is read back into its Operation by Mapping's own schema, `{ _tag: <its key, capitalized>, ...variables }` decoded by `Operation` (`#DEC-9`, `#DEC-12`), so an import, keyed `importTiles`, folds nothing, and fields the schema refuses fold nothing either, the server function refusing them in turn; building the Operation by hand from unchecked variables was the other way, refused because the variables reach the fold as `unknown`. A Reference's create folds under `pending-<turn>`, since the server makes its id; a Tile's create folds under the id its form chose, `crypto.randomUUID()` per submit, so a create refused and sent again never meets `TileIdTaken` (`#DEC-13`). The local refusal runs in the mutation function when the write's turn comes, on the cache's System alone: by then every write made before it has settled and its read has landed, the queue running one at a time, so that System already holds them. The read after a write refetches the System even while no page shows it (`refetchType: 'all'`), so a write queued while the user is on another page is not decided on a System missing the ones before it (cubic's local review on #79). It rejects with `Foreseen`, a `CallFailed` subclass in `calls.ts`, which the MutationCache carries to its channel as any refusal and `raise` does not report, since no call was made; a fifth constructor argument to `CallFailed` was the other way, refused for the parameter cap and the flag every other caller would pass. Every write's `onSettled` returns the invalidation, a refused one's included, so a write refused by the server shows until the read after it lands, the toast slightly ahead of the canvas, and the next write is decided on that fresh System; dropping a refused write at once would have decided the next one on the System the refusal said was stale. A foreseen refusal invalidates too, which reads the System again but sends no write. The gate goes from `System.tsx`, which no longer drops a click while a move or a swap is on its way: a second click on the slot a Tile just moved to is a move to where it stands, which changes nothing. The grow and shrink button keeps its own (`KindChange.pending`): the card shows the Tile of its new kind at once and offers the change back, so a double click would undo the first press (cubic's local review on #79). `useLeaveGuard(active)` sits in `ui/feedback/`, the folder with room for it and its test, beside the toast, called by `System` with `useSystemWriting()`, `useIsMutating` over the System's queue, an import included. MR-13: the tests that counted the System's reads now read what `useSystem` shows, the stand-in answering a second System, its Root retitled, once read again.

### DEC-16 `features/system/` regroups: the URL's model moves to `search/`

HEX-71. `features/system/` held six files, `System.tsx`, `TileActions.tsx`, `search.ts`, `tree.ts` and their two tests, and the ticket asks for room. `search.ts` and `search.test.ts` move to `search/`: what the page carries in its URL, the view and the change under way, a model of its own that `System`, `TileActions` and the route read, where `tree.ts`, the System as the canvas draws it, is read by Help's route too. The root keeps four files and gains a third folder beside `state/` and `import/`. The hook this ticket adds, what a refusal puts back, is a state hook, so it goes to `state/` beside `useCenteredTileState`, as the folder's convention puts one, and the root's two free places stay free.

### DEC-17 A refusal reaches the page through a MutationCache subscription; the change it puts back is read from its Operation; a reopened form lives while the URL holds its change

HEX-71. The ticket asks for one state hook that reads the refused System mutations (`useMutationState`, `status: 'error'`) and maps each back to its change in the URL. `useMutationState` answers a list to render from, not an event to act on once: a navigation made from that list while rendering is refused by React, and `useEffect` is out of features. So one listener per QueryClient (`takersFor`, `front/client/mapping/queries.ts`), made with its first System write or page, hands each write of the System's queue, the moment it turns `error`, to the pages open then: `useSystemRefusals` registers the caller's latest `take`, kept in a ref, once, through `useSyncExternalStore`, as the client bus's `useFact` subscribes. TanStack Query dispatches that only after the write's `onSettled`, so the read after the refusal has landed: the toast is out, the overlay no longer folds the write, and `Refused.system` is the server's System by then. Each `Refused` carries the Operation, read back by Mapping's schema as the overlay reads a pending one (`#DEC-15`), so an import, no Operation, is none, and `shown`, what its form shows (`shownOnForm`, exported from `channels.ts` for it). `take` answers whether the page shows it. A form's refusal on a field has the `fields` channel, which raises no toast, and its form closed when it was sent; so when no page open at that moment takes it back, none open or the page leaving it be, the listener has `unshown` (`channels.ts`) show it in a toast, and a field refusal is never lost nor shown twice: one place decides, at the moment of the refusal, where a first version counted the open pages in the write's `onError`, a network round trip earlier, and could miss a page opening or closing in between (cubic's local reviews on #80). `useRefusalState` (`features/system/state/`) maps the Operation to its change: a create to its slot's form, an edit to its Tile's form, a move to the move of its Tile, a swap to the move of the Tile it names first (`swapOf` and `movingIn` in `tree.ts`, which `System.tsx` sends it by), none for a Tile gone; a delete and a Reference's create or delete to nothing. A grow or a shrink is a `MoveTile` too: a move to the same Direction of the same parent, of the other kind, which no move under way makes (`slotOf` keeps a moving Tile's kind, or takes it into a Context), so such a move puts nothing back; telling them apart by the kind of slot alone would have misread a Leaf taken into a Context (cubic's local review on #80). Tagging the card's write in its mutation's meta was the other way, refused: the client's write hooks would carry a feature's distinction for one caller. The change applies to the URL of the moment the refusal arrives, through `SearchChange`'s function form, and only while no change is under way: a form or a move the user started meanwhile is theirs, and so is a change an earlier refusal put back, so the refusal leaves it be and shows in a toast (cubic's local reviews on #80); the view the user moved to meanwhile stays. The hook lives in `TileActions`, mounted with the page, so off it a refusal shows in its toast alone rather than pulling the user back home. The reopened form, its content and what it shows, is `useState` in the hook, answered only while the change under way is its own (`keyOf`), and let go the render the URL leaves it, closed, sent again, replaced or gone back from, so opening the same slot later starts blank; reading it from the MutationCache instead would have reopened a stale refusal for as long as TanStack Query keeps the mutation. An edit's content is the Tile as that System holds it with the fields the edit sent over it, since it sent only those that changed. The form is keyed by the refusal's turn, so each refusal opens it afresh, and shows the refusal as a refused submit would, through `openedOnRefusal`, which `ui/inputs/forms/form.tsx` gains for it: on mount, the fields it names touched and their errors set through TanStack Form's `setErrorMap({ onSubmit })`, which a change to the field clears; a refusal on no field is in its toast already. TanStack Form's API stays in `ui/`, where a first version had the feature call it (cubic's local review on #80); the ui list grows by this ticket's request, tested in `form.test.ts` and shown in `/dev/ui`. The Tile forms send through `mutate` and answer at once (`TileSubmit` takes the content, no `onSaved`), the form's `onSubmit` replacing `validators.onSubmitAsync`; `submitMutation` stays for `/dev/errors`, whose form still waits for its answer.
