# Decisions

### DEC-1 A Leaf slot is stored as 7 to 12 and named `{ leaf: n }`

HEX-53, [#61](https://github.com/Diplow/diplow/pull/61). The ticket asked for a Leaf slot space beside the Branch and Context slots and left its shape open. The `tile` table keeps one `direction` column, a Leaf in Direction n stored as n + 6, so the unique slot index covers the new slots unchanged, the direction check gains them (migration `leaf-slots`) and every existing row reads as a Branch; only `tile.ts` knows the offset (`rowDirection`, `leafOf`). Everywhere else, Mapping's `Slot`, the API's schema and the MCP tools, a Leaf slot is `{ leaf: n }`, so an agent and the client name a Leaf by the Directions 1 to 6 the language gives it, never by 7 to 12.

### DEC-2 A read answers `branches` and `leaves` where it answered `children`, and Help says nothing of Leaves yet

HEX-53, [#61](https://github.com/Diplow/diplow/pull/61). `SystemTile`, `ReadTile` and `openTile`'s answer carry `branches` and `leaves`, each by Direction: Child stays the word for either kind, so no field is named after one kind alone, and a Leaf is read as a Tile with nothing below it. The canvas keeps its own `children`, filled from `branches`, and draws no Leaf until M4. Help's notes still teach six Children at most, which is what the canvas shows; they learn Branch and Leaf once the canvas draws them.

### DEC-3 Mapping's Leaf rules and their tests live in `domains/mapping/leaves/`

HEX-53, [#61](https://github.com/Diplow/diplow/pull/61). `domains/mapping/` already held its six files, and `mapping.test.ts` sat at the 600-line cap once `children` became `branches` and `leaves`. The new `leaves/` holds `leaves.ts`, the two checks a change runs (`notLeaf` and `holdsNothingIfLeaf`), and `leaves.test.ts`, those checks on rows made by hand, then Mapping's operations on Leaves over PGlite. Like `help/`, it has no `CLAUDE.md` of its own: Mapping's folder table says what it holds.

### DEC-4 What a Tile keeps is checked by its type: a write takes only a decoded Name, Tile config and Frontmatter

HEX-54. The ticket asks that a bad Name be refused "when stored", `NameInvalid`, and leaves open which operation stores one, since the import (HEX-57, HEX-58) is not built yet. `createTile` takes the three, optional, beside the content, but typed as the branded types of three Effect Schemas in `domains/mapping/kept/kept.ts` (`Name`, `TileConfig`, `Frontmatter`): only a decode makes one, so nothing unchecked reaches the tiles repository, and `named` and `configured` give `NameInvalid` on the field at fault (`name` or `config`). Had `createTile` taken raw strings and refused them itself, its error type would have gained `NameInvalid`, and the MCP's `create_tile`, whose refusals are typed by its program's errors, would have had to teach agents a refusal no input of theirs can meet: neither the server function nor the MCP tool accepts the three. The Frontmatter schema's failure stays a Schema error, for the import to fold into `ImportRefused` among its faults; the ticket names no error for it. `editTile`, `moveTile` and `swapTiles` never touch the three: none of them passes one to the repository's `update`, which, speaking rows, would write any column it is given (cubic's local review on #62 asked that the rule stay Mapping's rather than the repository's type). The bounds live in these schemas, as DEC-8 of `hexframe-v0-mapping` keeps them in the API's: the migration (`tile-kept-from-files`) adds three nullable columns, `name` text, `config` jsonb and `frontmatter` json, with no check of their own; `frontmatter` is json because jsonb sorts an object's keys, and kept Frontmatter exports in the order its file gave (cubic's local review, round 2 on #62), as a JavaScript object holds it, so a key of digits alone comes first; since a byte count over jsonb would need raw SQL in the schema. `kept/` is a new folder because `domains/mapping/` held its six files.

### DEC-5 A Tile config is inherited part by part, and a folder pattern fills in at least one placeholder

HEX-54. "Inherited by everything below, until a Tile below sets its own" leaves open whether a config that sets only the file name keeps the folder pattern from above. It does: the naming in force at a Tile is each part its own config sets, else the nearest Tile above's, else the defaults (`CLAUDE.md`, `<n>-<slug>`), so a `.hexframe/config.yaml` lists only what it changes. The naming in force at a Tile includes its own config, as a folder's `.hexframe/` names the file beside it; which part names which file or folder is the serializer's (HEX-55). `Naming` is typed from the repository's `TileConfigColumn`, and the Schema's parts must name exactly its keys (`satisfies`), and the decoding Struct is built from those parts (`Struct.map`), so a new part is added in the column first and the compiler asks for its check. A config that sets no part is refused too, `NameInvalid` on `config`, so a Tile that sets its own config always has something for a `.hexframe/` folder to hold (cubic's local review, round 3 on #62). A Leaf may carry a config as any Tile does, and `namingOf` applies it; whether the serializer, which writes a Leaf as one file, honours or drops it is HEX-55's to settle. A folder pattern fills in `<n>`, `<slug>` or both, and the ticket's rule applies to the parts around them: each non-empty one is one path segment, so `<n>.<slug>` is refused for its `.` as `..<n>` is, and the whole pattern is at most 255 bytes. A pattern with no placeholder would name every sibling alike, so it is refused too. A kept string holds no line break of any kind (`\n`, `\r`, U+0085, U+2028, U+2029) nor another control character but a tab, and the key `__proto__` is never kept, since a reader assigning keys one by one would take it for the object's prototype. The 4 KB are the UTF-8 bytes of the map as JSON.

### DEC-6 Mapping writes YAML through `yaml`, confined to `domains/mapping/files/`, every value on its key's line

HEX-55. The ticket puts the serializer in `domains/mapping/files/` and asks for a YAML serializer, "a dependency like any other". `yaml` (eemeli, 2.x, stable, already in the lockfile through Vite) is no SDK: it reaches nothing outside the process. So Mapping imports it, and only from `files/`, where an export writes its files and an import (HEX-57) will read them: dependency-cruiser's `no-yaml-outside-mapping-files` holds it there, and `files/frontmatter.ts` is the one module that imports it so far. It writes with no line folding, a long double-quoted value's included, and no block scalars (`lineWidth: 0`, `doubleQuotedMinMultiLineLength: Infinity`, `blockQuote: false`), so a line break in a value is an escape, and it throws, a defect, on YAML holding more lines than keys (cubic's local review on #63 found `yaml` folding a double-quoted value of 40 characters or more at its escaped line breaks, which wrote a `---` line of its own). `yaml` still writes the Unicode line and paragraph separators raw, even double-quoted, and the shape's `linesOf` splits on them, so a value holding ` --- ` would have closed the block: a string holding one is written double-quoted with the separator as YAML's `\L` or `\P`. A test splits every file with the shape's `splitFrontmatter`, which needed the app to import the shape: dependency-cruiser now lets `src/domains/mapping/` import `2-claude-mod/hooks/shape/node.ts` and `exclusions.ts`, and nothing else of claude-mod, the first step HEX-57 lists, taken early because only a test imports it.

### DEC-7 How an export names a folder's entries

HEX-55. A kept Name is dressed for the slot its Tile stands in now, since a move keeps it: its leading dot and its `.md` dropped, then a dot put back for a Context folder and `.md` for a Markdown Leaf, so `3-games.md` becomes `3-games/` as the shape's Leaf grows into a Branch. A Tile without one is named by the folder pattern in force at its parent. Then any name, kept or made by the pattern, that the shape would not read back in its Direction takes its number: a numbered Name is renumbered to the Direction it stands in, and a bare name is kept only when the shape, seating the numbered names first and the others in the free Directions in name order, would seat it there again. Mapping holds Branches and Leaves apart, so each kind is seated among its own, as the shape's Branches and Leaves rings do; HEX-57's reader is to seat them the same way. A name also takes its number, put first even when it is numbered already, when it is a Branch's or a Leaf's starting with a dot, which the shape would read as Context or skip (a folder pattern `.x-<slug>` is a valid one; cubic's local review, round 3 on #63), when an entry before it in the folder (Branches, then Leaves, then Context) took it, or when the shape reads it as something other than an entry (the folder's own file in force, `CLAUDE.md`, `-CLAUDE.md`, `.hexframe`, `.git`, `node_modules`), however it is cased, since an import refuses two paths that differ only by case (cubic's local review on #63). A name still misread after three rounds, or one that is no path segment, throws: a defect, never written. A Leaf is written as its content alone, under its Name, only when that loses nothing: an import of a file that isn't Markdown made it (its Name isn't Markdown nor a dot file, its Title is that Name), its Preview is empty, and the naming leaves it its Name, since an import titles such a file by its name. Any other Leaf, a Branch shrunk into a Leaf or a `package.json` that had to take its number among them, is a Markdown file, `4-package.json.md`, so its Title and Preview survive (cubic's local review, round 2 on #63); a folder `3-x/` beside a file `3-x` in one Direction so writes the file as `3-x.md`. A test hands the names to the shape's `sortEntries`, each kind alone, and checks each lands in its Direction, so the export's seating and the shape's can't drift apart unseen.

### DEC-8 What an export's files say: its root, its configs, its References

HEX-55. The exported Tile's file sits at the export's root (`parent: .`), a Leaf's being the export's one file, named as its folder names it. A folder's own file takes the file name in force at its Tile, the config it sets included, checked again as one path segment and none of the shape's exclusions (`.hexframe`, `.git`, `node_modules`), else a defect (round 3 on #63), and its entries the folder pattern in force there, since its `.hexframe/` folder sits inside it. A Tile that sets its own config writes the parts it sets; the export's root also writes every part of the naming it inherits that isn't the default, so a subtree of `.skills/` reads back with its `SKILL.md` files. A Leaf has no folder for a `.hexframe/`, and its config names nothing it writes, so it is not exported (DEC-5 left it here). A Reference's file carries `title`, `parent`, `preview` and `reference`, and no `id`: its target's would give two files one id. `reference` links an exported target by its file's path, `.md` dropped, `[[1-leadership/CLAUDE]]`, as the vault's own wikilinks do and Obsidian resolves; any other target, a broken one included (title `broken`, empty Preview), by the link the caller builds from the target's id. The export is `exportOf(system, id, link)`, pure: the API layer reads the System, Help's included, and passes the link function.

### DEC-9 An export streams from a server function as a raw `Response`; Mapping zips it through the zip repository

HEX-56. The ticket asks for a server function that returns the zip as a streamed `Response`, and to check what the client gets back. Start 1.168 hands it over: a handler's `Response` is marked `x-tss-raw` and the client's fetcher returns it untouched, while any other answer is serialized as usual. So `exportTile` (`api/mapping/mapping.ts`) answers `asDownload` of its outcome (`api/mapping/download.ts`): on success a `Response` whose body is the archive's stream, `Content-Disposition: attachment; filename="<slug>.zip"`, `Cache-Control: no-store`; on failure the `Outcome` every server function answers. The client turns either back into an `Outcome` (`downloaded`), so `useExportTile` is a `write` like any other, its refusal in a toast, and saves the blob through a link it clicks; the browser holds the zip once, the function never does. No raw server route was needed, so server-foundations' DEC-18 stands. It is a GET, a read, signed in through the Session like every Mapping server function, and takes a `TileRef`, so a Help id is refused by its schema: the card that offers Export is the System's, and Help's page has none yet. The zip is Mapping's operation, `exportTile` in `domains/mapping/mapping.ts`: it reads the System, calls `exportOf` and hands the files to the `Zip` service (`repositories/zip/`), which the runtime provides, since the API layer takes from a repository plumbing only. `exportOf` now returns the exported Tile's slug beside its files, which names the archive (the Root's is the user's name, `tile` while untitled). `zipped` deflates one file per pull of the stream, through fflate's synchronous `ZipDeflate`, so the function writes the archive as the browser reads it. The API builds the link a Reference left out of the export points at, home centered on its Tile, `/?center=<id>`, on the origin the request reached (`tileLink`). Whether Vercel lets a streamed answer past 4.5 MB is not proven here: the project's previews failed before building during this run, so HEX-56#PARK-1 leaves that check, and the browser walk-through, to a human.


### DEC-10 An import reads its files into a plan in `files/import/`, through one module that calls the shape, and Help's vault goes through it

HEX-57. The ticket asks for a pure reader beside the serializer, its plan, `ImportRefused`, a skip list, Help read through it, and leaves their shape open. `files/` held five files, so the reader has a folder of its own, `files/import/`: `read.ts` (`importOf`), `plan.ts`, `shape.ts`, the one module of the app that calls the shape, and their two tests. `importOf(source, idOfLink)` is synchronous and returns an Effect `Result`, the plan or `ImportRefused`, so Help reads at module load and HEX-58 yields it in a program. A source is a folder, by its name and its files, or one file alone, whose root is a Leaf (`NothingToImport` when that file is a binary or a dot file). The plan names each Tile by the path it was read from, `''` for the root, which is how a fault, a skipped file and a Reference point at it; a Reference's target is `Inside` (a path of the plan), `Linked` (the id `idOfLink` reads from an app link, which the caller builds, as an export's `LinkOf`; HEX-58 checks it is the importer's) or `Broken`. Each Tile carries its Name (the folder's name for the root), config and Frontmatter already checked (`keepable`, guards over `kept.ts`'s Schemas), so HEX-58 hands them to `createTile` as they are.

How it reads, where the ticket's "as the shape reads" left room: Mapping holds Branches and Leaves apart, so the shape's `sortEntries` seats a folder's folders alone and its files alone, as DEC-7's export expects. Two names claiming one Direction are `DirectionClaimed` for every kind, even where the shape's Children ring would move the later Leaf to a free Direction, and more than six of a kind are `RingOverflows`; a ring at fault is still read, so the faults below it are listed too. Exclusions apply first, then binaries (bytes that aren't UTF-8 or hold a NUL, checked before the 1 MB, so a large image is skipped, not refused) and dot files are skipped before seating, so they take no Direction, as HEX-59's browser prunes them before the upload. A frontmatter is read with `yaml`, the library the export writes with, rather than the shape's scalar reader, so escapes, numbers and booleans read back as written; one that isn't YAML of keys and values, a list where a Tile reads text, or a kept value the Frontmatter schema refuses is `FrontmatterInvalid`. The Title, Preview and Reference are decoded by an Effect Schema, text or a number or a boolean written as text. Frontmatter and Body are cut by the shape's `splitFrontmatter`, so the Body's line endings come back as `\n` (cubic's local review on #65 asked that the cut not be worked out a second time). A blank Title takes the name, as a missing one does. A `.hexframe/` file holds 4 KB at most, and an `exclusions.yaml` 16 exclusions of 64 characters at most, since each is matched against every name of its folder and an upload must not buy unbounded work on the server (`FileTooLarge`, `ExclusionsInvalid`; cubic's local review on #65, rounds 1 and 3). One that can't be read, or a config with a key that is no part of the naming, refuses the import (`ConfigInvalid`, `ExclusionsInvalid`) where the shape's media warn and leave nothing out: an import that kept what its exclusions meant to leave out would create what the user didn't ask for. Only a Context folder's `reference` makes a Reference, matched as `[[path]]` against the files read, with or without `.md`, an alias or heading dropped, and only a file read as a Tile is a target, never a Reference's own (#65); in a Branch or a Leaf the key is one an export writes, dropped, and a Reference's folder that holds anything is `ReferenceHoldsSomething`. The depth bound, 16 folders below the root, is HEX-58's number, applied here (`TooDeep`); its count of entries, its bytes and its path rules stay HEX-58's. The Title's and Body's bounds of `hexframe-v0-mapping/decisions.md#DEC-8` moved from the API's schema into `tile.ts` (`contentBounds`), which the API now imports, so the import checks the same numbers. `ImportRefused` is not in `mappingFailures` yet: no server function answers it before HEX-58. The ticket's first step, the app's `tsconfig` and dependency-cruiser, was already taken by DEC-6; `tsc` follows the relative import, so `include` stays as it is. dependency-cruiser's `no-shape-outside-mapping` now holds the shape to `files/import/shape.ts` and Mapping's tests, so "one module calls the shape" is a rule, not a comment (#65, round 2). A folder's other own files beside the one read (`-CLAUDE.md` beside `CLAUDE.md`, `CLAUDE.md` beside a config's `SKILL.md`), which the shape reads as nothing, are reported as skipped, `Shadowed` (#65, round 2). Plain YAML scalars are read as YAML 1.2 types, so `code: 007` is kept as `7`: what an export writes reads back as written, which is the round trip the ticket asks for.

Help: `vaultOf` keeps its own rules, stricter than an import's (a note with a frontmatter and every field, a numbered folder name, one folder a slot), checked by the help repository's `noteOf` as before, then hands the notes that pass to `importOf`, each language's note in the place of its folder's `CLAUDE.md`, so French reads as English does. Each row takes its Title, Preview and Body from the plan, its Body trimmed as before, and its place from where the import seated it, its id its parent's and its slot, as before the paths of slots; a folder whose note was refused is left out. Help's own rule that every folder's name is a slot of its own stays a check on the names (cubic's local review on #65 asked, in round 1, for one way to place a row and, in round 2, for it to be the plan's). A fault the reader finds fails the build as a problem named on its folder, and then no row is read. Help's tests pass unchanged. The presence of every field is still checked on the note by the help repository's `noteOf`, where the vault's own fields are the repository's to name; the values come from the import's reader alone, so a note the two read apart (`title: a: b`) fails the build rather than reading two ways.

### DEC-11 An import is planned outside the transaction and landed in one batch; the zip seam reads its own central directory

HEX-58. The ticket asks for `importTiles` in a new folder of Mapping, a bulk insert, a bounded unzip in `repositories/zip/`, the path rules and the server function, and leaves their shapes open. Mapping's new folder is `landing/`, `domains/mapping/` holding its six files: `archive.ts`, the bounds and the verdict on an archive's entries, `landing.ts`, and their tests. An import is two operations the API composes: `planImport`, the upload read into a plan through the `Zip` service, run outside any transaction so no connection waits on inflating; then `importTiles`, the plan landed as a change, in the transaction `programs.ts` opens. `mapping.ts` exports `changing`, `freeSlot` and `untitled` for it, and the API imports `landing/landing.ts` directly, so the two modules don't import each other.

The zip seam reads the central directory itself rather than through fflate's `Unzip`, whose entries carry no external attributes, so a symlink could not be told from a file. Each file inflates through fflate's streaming `Inflate`, fed a kilobyte of compressed data at a time, so one push inflates to about a megabyte at most before the count stops it; the headers' sizes are never read. An archive in zip64, encrypted, or with a method other than stored or deflated is `ArchiveUnreadable`, which no upload of 4 MB needs. A name is decoded as UTF-8, else, when not flagged UTF-8, one character per byte. The bounds are Mapping's (`archiveBounds`), in decimal as the shape's `readLimit` is: 2,000 entries, folder entries counted, 1,000,000 bytes a file and 16,000,000 in all. An entry past 1 MB stops the unpacking (`FileTooLarge`), as the ticket asks, so a binary over 1 MB inside a zip refuses the import where a file list skips it (DEC-10): HEX-59's browser leaves binaries out before it zips.

Each entry gets one fault at most, the first that holds: `Symlink`; `PathAbsolute`, `DrivePrefix`, `Backslash`, `DotSegment`, `PathNotNormal` (an empty segment, or a path NFC would write another way); `TooDeep`, more than 16 folders above it, as the reader counts folders; `PathsClash`, compared with `toLowerCase`, for two entries with one path, a file and a folder with one path, or a folder above an entry spelt two ways, the later entry at fault. A folder's own entry adds nothing once judged. The archive's root is the folder, as an export writes it, named by the upload, `.zip` dropped: a zip that wraps its folder in one more (macOS's Compress) lands that folder one level down, and unwrapping it is the browser's, which re-zips every import (HEX-59).

The server function takes a form (`Schema.fromFormData`): `upload`, the file, `as`, `Zip` or `File`, and `place`, `{ _tag: 'Slot', parent, slot }` or `{ _tag: 'Root' }`, as JSON, since a form holds strings; the client encodes its form by the same schema. Its program refuses an upload past 4,000,000 bytes before it reads a byte or asks who sent it, as `ImportRefused` with the fault `UploadTooLarge` on the path `''`; the limit is Mapping's, an import bound beside the archive's (`uploadLimit`, `fitsUpload` in `landing/archive.ts`), and the API calls it first, so Mapping never declares a fault it doesn't set (cubic's local review on #66); so the refusal reaches the client with its reason rather than as the `Unexpected` a failed schema gives. Start reads the form whole before any handler runs; Vercel's 4.5 MB cap is what bounds that read. `ImportRefused` joins `mappingFailures` and the message table, in English and French.

Where it lands: a Leaf slot takes only a plan whose root is a Leaf, one file alone, else `LeafHoldsNothing` (`onlyALeafIn`, in `leaves/` with Mapping's other Leaf rules, #66); one file in a Branch or a Context slot lands as a Tile with nothing below it. A System is empty when its Root is untitled and holds nothing; landing as the Root adds the Root first if it was never read, and a System holding anything is `DirectionTaken`, the Root's place taken. The plan's root gives the Root the five parts the ticket names, its Title, Preview, Body, config and Frontmatter, not its Name, which names nothing an export of the Root writes. A plan's content is not checked again: `importOf` bounds every Title, Preview and Body.

References: one `Inside` the plan points at the new Tile, the Root's own id when the plan's root replaced it; one `Linked` lands on that id only when the locked rows hold a Tile of it, not a Reference; anything else is written with a target the repository makes, a fresh id that names no row, so another Account's id is never stored. `tileOfLink` reads a link back as `tileLink` builds it: the request's origin, the path `/`, and a `center`.

The bulk insert is `Writes.insertAll`: rows named by keys of the caller's (the plan's paths), each under a row of the batch or a stored one (`RowRef`), a target the same or `Nowhere`; the repository makes every id, as it makes every other, and writes 500 rows per statement, so a row must come after the row it stands under, else a defect. The answer is `{ id, tiles, references, skipped }`: the Tile the import landed as, the Tiles it wrote, the Root among them when replaced, its References, and what it skipped. The import is no MCP tool, as the ticket says; nothing a user sees changed, so no browser check was due.

### DEC-12 The browser prunes an import through plain functions of `api/mapping/files/`; its refusal is its form's

HEX-59. `api/mapping/` held its six files, so `files/` now holds a System's files crossing the wire both ways: `download.ts` and its test, moved, the import's wire test (`import.test.ts`), moved, and `upload.ts`, the browser entry the ticket asks for, with its test. `upload.ts` is no server function: `prepared` takes what the user gave (`Given`: a folder by its files, each read only when asked, a zip, one file) and answers what to send or why the server would refuse it. It reaches Mapping's pure modules only, `files/import/read.ts` and `landing/archive.ts`, never `landing/landing.ts`, whose imports reach the database (`build`'s bundle check would fail), and the zip repository's `unpacked` and `archived`, as observability's plain functions reach the browser.

A folder is pruned in two passes, so a vault's `node_modules` is never read: by names first (`leftOutOf`, Mapping's, beside the reading in `read.ts` so the two can't drift), with a folder's `exclusions.yaml` read before anything else (`isSettingsFile`), then by bytes (`skippedAsBinary`, which never skips a folder's settings); a file past the shape's 1 MB is judged by its first 8 KB, so a large image is left out as a binary while a large text is refused as `FileTooLarge`, its whole never read; files are read one at a time, and reading stops once the texts pass the server's bounds, which refuse them anyway. What remains is checked by size against the bounds the server unpacks within (`pastBounds`, new in `archive.ts`), then by Mapping's verdict on every path (`pathFaults`, which `folderOf` runs on the server), zipped (`archived`, new in `zip.ts`) and refused past 4 MB. A zip the user gave is unpacked in the browser within bounds of its own (100,000 entries, 256 MB), far past the server's, so one zipped with its `node_modules` still reads, pruned the same way, and, as DEC-11 left to the browser, its one wrapping folder (macOS's Compress, its `__MACOSX` dot files left out) is unwrapped and names the import, by Mapping's `wrappingFolder`; where it stopped unpacking is Mapping's `stoppedAt`. Each rule is Mapping's, the browser only composes them (cubic's local review on #67). One file is sent as it is. What was left out is listed as `LeftOut` (`Excluded`, a folder once; `DotFile`; `Binary`) beside what the server skipped. The server decides everything again.

`ImportRefused` is `Invalid` on `files`, so it takes the channel table's `fields` row: the import's form is its files, and its drawer is where they show. A mutation can't use `submitWrite`, which only hands its form a sentence, so `settleSubmit` (`front/client/channels.ts`) answers a submit's value or its `Invalid` failure, typed among the call's own (`Submitted`), faults included, and throws any other for the mutation's channel; `submitWrite` is now built on it. A slot taken meanwhile, or a System no longer empty, gets a sentence of its own under `importTiles` (`DirectionTaken`, scoped).

The change is in the URL like `add`: `import=<parent>&slot=<slot>`, or `import=root` for an empty System's Root, `root` never being a Tile's id. An empty slot's drawer offers New tile or Import here, the same slot either way, since a feature adds nothing to `ui/` and the canvas's slot click has one action. An empty System is an untitled Root with nothing below it, as `importTiles` checks it, and the front's `isEmptySystem` says it again on the System it reads, stricter: a Root holding a Preview or a Body, written before its name, isn't offered the import, which would replace them. It only decides whether the Root's card offers the import; the server refuses a System that isn't empty with a sentence of its own, and still takes an untitled Root with a Body as empty, HEX-58's rule, so a link to `import=root` can replace that Body.
