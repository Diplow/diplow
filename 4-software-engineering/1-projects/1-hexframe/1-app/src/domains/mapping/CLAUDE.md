# mapping

The core domain, the one hexframe exists for. Someone maintains a system (a codebase, a team, their own life) and wants AI to work along their intent. Mapping lets them lay that system out as a hierarchy where what comes first is what matters most: a reader, human or agent, sees one Tile, then the six it breaks into, then theirs. Choosing what to show first is the exercise, and the hierarchy it produces carries the intent.

The language, as [[4-software-engineering/1-projects/1-hexframe/STACK|STACK]] first told it:

- **System**: the whole hierarchy a user maintains. An Account has exactly one, and its **Root** tile is the user: there is no profile beside it. The Root's Title is the user's name everywhere in the app. Mapping adds the Root the first time a System is named (`starOf`), idempotently, so no lost event can leave an Account without one; it starts untitled, until the user names themselves. The Root is the System's **star**, and its id names the System; the System's owner, which every row carries, is an opaque id to Mapping, an Account's today, an Organization's later. Mapping holds a System **flat**, its aggregate: its Root apart, every Tile and Reference below it by id, each with its parent and its slot, and whether an Account owns it, the shipped Systems' owned by none. Its **tree**, the Root with its Children and Context nested below it, is a view, built from the flat System for drawing and for writing a Tile as files. *Hexframe* is the product and the form, never the thing a user owns.
- **Tile**: the unit. A **Title**, a **Preview** (at most 350 characters: what a reader needs to decide whether to open it) and a **Body** in Markdown.
- **Version**: a Tile's count of the events that touched it, 1 once created. An edit, a move and a swap count on each Tile they change, a Reference's create and delete on the Tile whose Context slot they change, a Reference having none of its own; a create counts on no parent, nor a move on the parents it leaves and joins. Every read carries it, and an export writes it in each Tile's frontmatter, where an import drops it like `id`. Every Operation on an existing Tile carries the Version its writer read of it: an edit, a move and a delete their Tile's, a swap both Tiles', a Reference's create and delete the Tile holding the slot. `decide` refuses one that changed since, `TileChanged` (Conflict), so no writer, the user in another tab or an agent mid-Turn, overwrites what it never saw: it reads again, then writes (`hexframe-app-assistant/decisions.md#DEC-3`). The **System's Version** is the System's own count of its events, 0 before the first: `evolve` counts every event on it, an Operation's and an import's, one each, whatever it changed, and the service writes it on the Root's row, under the Root's lock, so two changes never share one. A client polls it, the smallest read there is (`systemVersion`, through the API layer's `latest`, beside the Conversation's last Entry), to know when to read the System again (`hexframe-app-assistant/decisions.md#DEC-6`).
- **Child**: a Tile in one of its parent's six **Directions**, which say what the parent does and how: 1 NW, 2 NE, 3 E, 4 SE, 5 SW, 6 W. The **Opposite** direction, three away, is a tension the parent balances. A Child is a Branch or a Leaf, as a vault has folders and files, and a Tile holds up to six of each, in their own six Directions: a Leaf and a Branch may share a Direction (how a canvas then draws them is [[4-software-engineering/1-projects/1-hexframe/1-app/src/front/ui/canvas/CLAUDE|canvas]]'s). A seventh Branch, or a seventh Leaf, is refused: the user regroups some Children under a new one, by moving them. That regrouping is the exercise, not a workaround.
- **Branch**: a Child that holds Children and Context of its own. Every Child made before Leaves existed is a Branch.
- **Leaf**: a Child that is one file, a Title, a Preview and a Body with nothing below it and no Context, so `STACK.md` reads as `STACK/CLAUDE.md` would with nothing beside it. Nothing is created under a Leaf. A Leaf grows into a Branch by moving to a Branch slot, and a Branch with nothing below it shrinks into a Leaf the same way; a move or a swap that would leave anything below a Tile in a Leaf slot is refused (`LeafHoldsNothing`, Conflict). A Leaf that isn't Markdown keeps its content verbatim as its Body, its file name as its Title.
- **Context**: what a Tile *is*, where its Children say what it does. Up to six Context slots, −1 to −6, in the same Directions; each holds a Tile of its own or a Reference. A codebase's Children are its frontend, backend and CI; its Context is the principles it follows.
- **Frame**: a Tile together with its Children.
- **Reference**: a link from a Context slot to another Tile, by id, so it survives a move. A Reference to a deleted Tile shows as broken; it never blocks the delete.
- **Operation**: a change to a System described as data, before it runs. A closed union of `Schema.TaggedClass`es: `CreateTile{id?, parent, slot, title, preview, body}`, `EditTile{id, version, …}`, `MoveTile` (a Tile and everything below it), `SwapTiles{a, aVersion, b, bVersion}` (two Tiles trade places, each with everything below it), `DeleteTile`, `CreateReference` and `DeleteReference`, each naming its holder's `parentVersion` (Leaves' create, grow and shrink are a create or a move to a Leaf slot). The server functions' inputs, the MCP tool table's `operation`, the message table's scope and the timeline's verbs derive from it. An Operation's name is its tag in camelCase (`swapTiles`), which the service's function that runs it, its server function and its MCP write share. **Who makes a Tile's id**: a `CreateTile`'s caller, when it carries one, so the client draws the new Tile, centers on it and names it in a queued write before the server answers; Mapping's service otherwise, as for every Reference (`Tiles.newId`, as the MCP's `create_tile`, which takes none, has it). `decide` is given the id and never makes one. A Tile's id is its own across every Account, so one taken already, in this System or another, is refused `TileIdTaken` and nothing is written, the same id sent twice included: no create is replayed. A clash on an id Mapping made is a defect, never a refusal.
- **Event**: what a change did to a System, a fact in the past tense, a `Schema.TaggedClass`: an Operation's, `TileCreated`, `TileEdited`, `TileMoved`, `TilesSwapped`, `TileDeleted` (which says the Title its Tile had, since no reader finds it once gone), `ReferenceCreated`, `ReferenceDeleted` (`OperationEvent`), and an import's, `TilesImported`, the Tile it landed as and how many Tiles came with it, below it; one closed union, `MappingEvent`. It says what changed in the System and nothing of who changed it: no Account, no Session, no Key. An Operation makes none when it changes nothing. `TilesImported` is the one event no Operation makes: the import's plan makes it once landed (`importedAs`, `files/import/plan.ts`), the one exception to `decide` making every event. The service publishes on the bus every event it wrote, an import's as an Operation's, whichever door ran it; the API layer's bus holds them until the transaction commits and puts who acted on their envelope, so a refusal or a rollback publishes nothing. **Mapping's summary** of an event (`summary`, on `summaryOf` and `changeOf`, pure, in `operations/events.ts`) is what a timeline tells of it: a change, its verb, the event's tag, the Tile it is about with its Title and the other Tile a swap traded places with or a Reference points at; or an import, the Tile it landed as and how many Tiles came with it; the API layer hands it to the Assistant, which knows no Tile.
- **Batch**: Operations kept to run later, written nowhere until they run (the Assistant's Proposal is one), each added in Mapping's words (`addToBatch`), never "drafted", a word of the Assistant's (`hexframe-app-assistant/decisions.md#DEC-20`), each decided once already, a create with the id of what it makes given then (`Batched`). Its **fold** over a System (`fold`) is the System it would make: each Operation decided on what the ones before it made, one that no longer applies, a Tile changed or gone since, left out with its refusal and the rest folded. Run for good, a batch is all or nothing, and so is adding to it: once one of its Operations no longer applies, it is `BatchOutdated`, refused whole. Its **inverse** (`inverse`, `Undo`) is what undoes it once it ran, made from the System it ran on: an Operation per event, the last event's first, an edit's previous fields, a move's previous slot, a swap's swap, a create's delete, a delete making again what it removed under the same ids, a Reference's own, each naming the Version the ones before it leave, the first ones the Versions the batch left, so an undo over a Tile changed since is refused by `decide`, the whole `BatchOutdated`, and so is one that would delete a Tile it made while anything lies below it, which another writer put there since (`undone`). A batch that runs in several goes (the Assistant's Turn in apply runs one) keeps one undo of all of them (`extended`), `Outdated` for good once another writer changed a Tile it touched between two of them (`hexframe-app-assistant/decisions.md#DEC-16`).
- **Decider**: Mapping decides in two pure functions. `decide(system, operation)` answers the events an Operation makes on a flat System, or the refusal it gets, a create given the id of what it makes, which `decide` never makes; `evolve(system, event)` answers the System after one event. Every rule of an Operation lives in `decide`, and only there: the service runs it on the System it locked before it writes, the client on the System it holds before it sends, so the two never disagree on what an Operation does.
- **Right**: what someone may do on a Tile: *read* it; *write* it, which includes *read*; and *@*, which includes *read*, may run the agent at it. *write* and *@* are independent: an *@* without *write* grants no write.
- **Grant**: a Tile's value for one **subject**, an Account, a Group or **Everyone**, each but Everyone an id opaque to Mapping: *none*, *read*, *read+write*, *read+@* or *read+write+@*. **Inherit** is every subject's default on every Tile, never stored: the value comes from the parent. A star inherits nothing, so a subject without a Grant there has *none*. What someone may do on a Tile is, for each subject covering them (themselves, each of their Groups, Everyone), the nearest explicit value walking up, then the union of those: an explicit *none* denies one subject only. Everyone is anyone holding the link, signed in or not, and reads at most: a Grant giving it more is no Grant (`Grant`'s Schema refuses it, the table's check too, and the resolution reads it as *read* at most). A Grant whose subject no actor carries any more, a deleted Group's, resolves for nobody, with nothing written to clean it up. Deleting a Tile deletes its Grants.
- **Actor**: who acts, as the API layer hands Mapping over, fresh for every request and every MCP call, never cached: their Account, the Groups they belong to, the owners they stand for (their Account, and later the Organizations they are an admin of) and whether a Session proves the request, rather than a Key, a Turn's Key or an agent. Mapping imports nothing from IAM to know it.
- **Owner**: whoever the System's owner id names, and every actor standing for it: every right, no Grant needed, and, later, the only one to change Grants, from a Session only.
- **`may(actor, sharing, tile, right)`**: the rights decision, pure, beside `decide` in `operations/`, on a System as its rights are read (`Sharing`: its owner, where each Tile stands, its Grants). Before `decide`, the service asks what the Operation needs (`allowed`): *read* on every Tile it names, *write* on the Tile it changes, on the parent it creates under, on every Tile a delete, a move or a swap carries and on the parent each lands under. A move stays inside its System. A move or a swap that would let a carried Tile be read by a subject that could not read it before changes who sees what, as a Grant does: it takes the owner, from a Session; anyone else, or the owner through a Key, a Turn's Key or an agent, is `NotAllowed`. Without *read*, a Tile is `TileNotFound`, so an id still says nothing; two things are seen without it, deliberately, a star's card (with HEX-126) and `TileIdTaken` on a create under a chosen id. With *read* but not the right asked, `NotAllowed`, which never says which Tile.
- **Shipped System**: a System hexframe ships, which no Account owns: every Account reads it, none writes it. Each is the same thing told apart by its Root, whose id is the name of the folder it is written in, and two ship so far: **Help**, hexframe's guide (`help`), and the **tutorial**, a new account's first journey (`tutorial`).
- **Name**: the folder or file name a Tile was imported with (`STACK.md`, `3-games`, `-CLAUDE.md`), kept so that it exports under it again and the `[[wikilinks]]` in Bodies still resolve. Editing the Title never changes it, nor does a move or a swap. It is **one path segment**, as is every name a Tile config sets: never `.` or `..`, no `/`, `\` or control character, at most 255 bytes (`NameInvalid`, Invalid, when it is stored).
- **Tile config**: what a `.hexframe/` folder holds, carried by a Tile and inherited by everything below it, part by part, until a Tile below sets its own. It holds the naming: the file's name (default `CLAUDE.md`) and the folder pattern (default `<n>-<slug>`, filling in at least one of `<n>` and `<slug>`, the parts around them each one path segment), at least one of the two set, so a `.skills/` subtree exports its files as `SKILL.md`. The **naming in force** at a Tile is what its own config sets, else what the nearest Tile above sets, else the defaults.
- **Frontmatter**: the keys an imported file carried that a Tile has no use for (`owner`, a skill's `name` and `description`), kept as they came. Mapping never reads them, but bounds them: a key of `[A-Za-z0-9_-]`, 64 characters at most, never one an export writes itself (`id`, `title`, `parent`, `preview`, `version`, `reference`); a string on one line, a number or a boolean as its value; 32 keys and 4 KB per Tile at most.

Only an import sets a Name, a Tile config and Frontmatter: no screen edits them, and no change after `createTile` touches them.

What a user does *to look* at a System is not Mapping: centering on a Tile, expanding and collapsing a Frame, showing the center Tile's Context. It is view state, owned by the URL, so a link shows exactly what its sender saw ([[4-software-engineering/1-projects/1-hexframe/1-app/src/front/ui/canvas/CLAUDE|canvas]]).

## Rules

- **Who acts is not whose System it is.** Every read and every change takes `{ actor, system }` (`Acting`): the actor, the owners it stands for, which the API layer reads from IAM's proof of the request (by a Session or a Key), never from what the caller sends; and the System, named by its star, which the API layer resolves from the request, for now always the signed-in Account's own. The service finds a System's Tiles by the System, never by who acts, and asks `may` what the actor may read and do there, from the Grants its Tiles carry, read on every request: a Tile they may not read is `TileNotFound`, as is a star that names none (`hexframe-app-sharing-organizations/decisions.md#DEC-1`, `#DEC-2`). A read of the System whole (`system`, `systemVersion`, `exportTile`, `systemFiles`), a batch and an import are its owner's alone, until the System is read as the actor may see it (HEX-126) and a Turn runs elsewhere (HEX-134).
- **An Account sees its own System, the shipped Systems, and what a Grant lets it read; it writes its own, and what a Grant lets it write.** A Tile it may not read is `TileNotFound`, as a deleted one is, so an id says nothing about whether it exists; one it may read but not change as asked is `NotAllowed`, which says nothing of which Tile held it back. The one exception is a create under an id its caller chose: `TileIdTaken` says that a Tile has that id, never where nor whose, since ids are unique across every Account and the client draws its fresh ids at random. Help and the tutorial are read by every Account, and by anyone on home, signed in or not, and written by none: each comes from its folder in the repo, `1-app/help/` and `1-app/tutorial/`, in English and in French, bundled at build time, never from the database nor a Mapping write, and nothing reads the file system at request time. Mapping refuses a write that names a Tile of either (`ShippedReadOnly`, Forbidden) whatever schema the caller passed through, a move or a swap with one end in one included: the service decides such an Operation on the System it names, which no Account owns, and `decide` refuses every change to a System no Account owns, so the rule reads the System, never `help/` nor `tutorial/`. A shipped System's id is a path from its Root, looked up in the bundled set of Tiles, never read as a file path. A Reference, for now, points at a Tile of the same System: public Tiles, which anyone can refer to, come with sharing.
- **A change sees the System alone.** It first locks the System's star, its Root (`Tiles.lock`), loads the System flat as it stands, a shipped System's instead when the Operation names one of its ids, asks `decide`, then writes one change per event (`insert`, `update`, `swap`, `remove`) and the System's Version, all in one transaction. Two changes to one System never interleave, so a slot never holds two Tiles and a move never makes a loop. Mapping neither opens nor commits that transaction: the API layer does (`transactional`), as it will for one that spans domains, and every change's type requires it (`InTransaction`), so none can run outside one. The lock is Mapping's decision, the query the repository's errand (`hexframe-v0-mapping/decisions.md#DEC-3` in the run's registers, where the repository still opened the transaction).
- **The Root is the user.** It is never moved nor deleted (`RootFixed`), and its Title is edited like any Tile's. IAM is to keep a copy of it for emails, but no email is sent yet, so none is kept: `editTile` publishes `TileEdited`, which nothing subscribes to yet, and Better Auth's name stays empty. The first email brings the event, the Root's rename on the bus, and the API layer wires IAM to it (`hexframe-v0-mapping/decisions.md#DEC-4`).
- **A swap trades two places whole.** Each Tile takes the other's parent and slot, a Branch's, a Leaf's or a Context slot alike, with everything below it, so a full ring still lets two Tiles trade. Neither may be the Root (`RootFixed`), nor lie below the other (`MovedUnderItself`), nor take a Leaf slot while it holds anything (`LeafHoldsNothing`), and a Reference has no place of its own to trade (`TileNotFound`). A swap of a Tile with itself changes nothing, as a move to where a Tile stands does.
- **A Reference is where it stands.** It has no content, and no operation but its create and delete, both by its slot: to put one elsewhere, delete it and create another. Moving the Tile that holds it carries it along; deleting the Tile it points at leaves it broken.
- **A Body is read only when asked.** `readTile` and `openTile` walk down one generation per query and select only the fields asked, the opened Tile's apart from those below it, so a Body nobody asked for never leaves the database: `openTile` reads the Body of the Tile it opens, when asked, and never its Children's. A Reference shows its Tile's id, Title and Preview whatever was asked, the least a reader needs to decide whether to open it (`hexframe-app-mcp-server/decisions.md#DEC-8`).
- **Rights are asked before `decide`.** The service asks `allowed` on the System it locked, with the Grants as they stand under the lock, then `decide`, so a refusal of `decide`'s, a slot taken or a Version gone stale, never tells of a Tile the actor may not read. `may` reads no Operation's rule and `decide` no right: an Operation is the same change whoever makes it.
- **Every rule of an Operation lives in `decide`.** The service checks nothing beside it but who may make it, and the client asks it rather than knowing a rule of its own (`swapsWith`, `front/features/system/tree.ts`). A rule `decide` reads is a plain function of the System returning a `Result` (`checked`, `notLeaf`, `holdsNothingIfLeaf`, `freeSlot`), never an `Effect`, so the browser runs it as the server does. One refusal is no rule of the System: a create's id taken, which only the whole table knows, since a Tile of another Account's may hold it. The write finds it, by the table's key, and the service answers `TileIdTaken`; the client, which chose a fresh id, never meets it but by sending a create twice.
- **An Operation is checked twice, by two owners.** Its schema bounds what it carries, a UUID for every id, a slot among the six of its kind, every string within its bound, so nothing unbounded reaches the service; `decide` rules on what the System lets it do. A schema a caller got past changes nothing: the service still refuses a shipped System's id (`ShippedReadOnly`).
- **A write names the Version it read.** Every Operation on an existing Tile carries it, and `decide` checks it right after finding the Tile, before any other rule but the Root's, so a write over a Tile changed since, by anyone, is refused `TileChanged` and writes nothing, the no-ops included. The service writes each Tile at the Version `evolve` gives it, so the database and the client's overlay never disagree on one.
- **Only the fields given are checked**, so the Body of an untitled Root can be written before its name. A Preview's 350 characters are counted as a reader counts them, an emoji of several code points being one.

## The MCP server

An agent works on a System through the MCP server, with a Key ([[4-software-engineering/1-projects/1-hexframe/1-app/src/api/server/mcp/CLAUDE|mcp]]). It reads in the order a human discovers it, through `openTile` and `readTile`: `open_tile` opens one Tile with its Children's and its Context's Titles and Previews, `map` shows several generations of Titles and Previews at once, and a Body leaves the database only when asked. It changes the System through a write tool per Operation, each taking the Operation's fields and running it for the Account its Key proves, with the same refusals. Help reads the same way and refuses every write; the MCP's reads take Help's ids, not the tutorial's, which only home shows.

## Later

Sharing and export take a Tile as their entry point, and everything below it comes along. A Tile can be public by link, so any LLM that can fetch a URL can read it.

- **Files, read as the shape reads them** (built, `files/import/`): Mapping imports the shape's reading rules (`node.ts`, `exclusions.ts` in `2-claude-mod/hooks/shape/`) by relative path, as the Obsidian plugin does, so a folder reads into Tiles by the same rules in every medium. It is the one place in the app's domains and API that may, and within Mapping one module calls the shape and returns Mapping's own types, so the shape's never reach an operation or the API.
- **Names, exported**: a numbered Name follows the Tile's Direction; an unnumbered one stays bare as long as an import would put it back in the same Direction. A Tile without one is named by the folder pattern in force, its slug the Title in `[a-z0-9-]` only, `tile` when nothing is left, and its file by the file name in force. An export checks every segment it writes again (`isSegment`), kept, set by a config or made from a Title, so it never writes outside its root; a Tile that sets its own config gets a `.hexframe/` folder.
- **Frontmatter, exported**: written back after the keys an export writes itself, through a YAML serializer, never by joining strings, so no value can open a key of its own. An import drops a key an export writes itself before keeping the rest.
- **Export**: a Tile and everything below it, written as a zipped folder (the files: `files/`): a folder per Branch, `<n>-<slug>/`, and per Context tile, `.<n>-<slug>/`, holding one Markdown file whose frontmatter carries the Tile's `id`, `title`, `parent`, `preview` and `version`, then its Body; a file per Leaf, `<n>-<slug>.md` with the same frontmatter, or its content alone when it isn't Markdown and writing it bare loses nothing: its Title its file's name, no Preview, its Name kept (`hexframe-app-import-export/decisions.md#DEC-7`). Mapping decides the files; zipping them is a repository's errand, done as the download streams (`exportTile`, built), and handing them to another domain (the Assistant's sandbox, `systemFiles`, built) is the API layer's. Where a Tile lives in the System's export, its folder and its file, is Mapping's to answer too (`placesOf`), since the names in force and the numbering are its own: a Tile moved or renumbered is found where the files put it.
- **Import**: (built: its reading, `importOf`, `hexframe-app-import-export/decisions.md#DEC-10`, its landing, `landing/`, `#DEC-11`, and the screen, an empty slot's or an empty System's, whose browser leaves out what the reading would before it uploads, `#DEC-12`) a zip or a folder read back the way the [[4-software-engineering/1-projects/1-hexframe/2-claude-mod/hooks/shape/CLAUDE|shape]] reads a vault: a repository unpacks it and says what each entry is, Mapping reads the files and gives the verdict, and an upload past 4 MB, the bound Mapping sets below Vercel's 4.5 MB cap on a request (`fitsUpload`), is refused by the API layer before either, landing as a new Tile in one empty slot of the Tile chosen, or as the Root of an empty System. It is a write, so an import into Help or the tutorial is `ShippedReadOnly`; Help exports like any Tile, since every Account reads it. It always creates: the `id`s it reads are ignored, so importing twice makes two copies. What the shape already settles is repaired (a folder without a title takes its name, an unnumbered name the first free Direction); anything else wrong refuses the whole import (`ImportRefused`, Invalid, carrying every fault at once), and nothing is written: a file too big for a Body is refused, never cut, and so is an import past its bounds (its number of files, its depth, and the bytes it unpacks to, counted as they inflate rather than taken from the archive's headers), or holding an entry whose path isn't plain: a symlink, an absolute path, a drive prefix (`C:`), a backslash, a `..` or `.` segment, a path that doesn't read the same once normalized, or two entries whose paths are equal or differ only by case. An archive is unpacked in memory only, never onto a disk. A `reference:` resolves only to a path inside the import or to a Tile of the importer's own System; anything else lands as a broken Reference. Mapping's reading decides what is excluded; a client may leave the same names out before uploading, to save the upload, never instead. Only what a System cannot hold is skipped and reported: binaries and dot files, and a folder's other own files beside the one read, which the shape reads as nothing.
- **Reference, exported**: a Context folder whose file carries its target's title and Preview and `reference: "[[path]]"`, the path from the export's root. A target outside what is exported is linked by its URL in the app instead, built by whoever calls the export, never by Mapping, so it resolves only back in the same System. A `[[wikilink]]` written in a Body stays text: a Reference lives in a slot, never in a Body.
- **Fold and inverse** (built, the Assistant project, `operations/batch/`): pure functions beside the Decider, Operations folded over a System, the System they would make, and a batch's inverse, the Operations that undo the events it made, from the System it ran on. The API layer is what shows a fold to an agent, runs a batch and runs an inverse ([[4-software-engineering/1-projects/1-hexframe/1-app/src/api/CLAUDE|api]]).
- **Exclusions**: an import reads a `.hexframe/` folder's `exclusions.yaml` to leave its names out, then forgets it: a System has no files to exclude, and a Tile config holds only the naming.

Not yet, after Import & export: an import that updates the Tiles whose `id` it reads instead of copying them; a screen to edit a Tile's Name, config or Frontmatter; an import past 4 MB, uploaded to storage first; binaries.

What sharing brings next, as the grill of 2026-10-17 settled it ("hexframe app: Sharing & organizations" in Linear, HEX-124 to HEX-140); rights, Grants, `may` and the actor are built, above:

- **Star**: the Root of a System, whose owner Mapping knows by an opaque id. Its Title and Preview, its card, are seen by anyone, which is what lets a star be named; nothing else of a System is, without a Grant. A star's id is its **Handle**: naming someone is naming their star.
- **Grants changed** by the owner only, from a Session, never through a Key, a Turn's Key or an agent (the Share widget, HEX-128, HEX-131). Who stands for an owner beside the Account itself is not Mapping's to know.
- **The System as the actor may see it** (HEX-126): the whole read, its Version and an export reading what the actor may, not the owner's alone; and a batch and an import writing as the actor may, with a Turn on someone else's Tile (HEX-134).
- **Across Systems**: a Tile someone may read is visited on the canvas, its Breadcrumb from its star. A Context slot refers to a Tile of another System when its creator may read the target; whether a reader sees the target or an unavailable Reference is decided for that reader on every read.
- **Shipped**: Help and the tutorial, still read from the bundle, become Tiles under the Hexframe star. Being shipped is what makes a Tile read by Everyone and written by nobody, its owner included, and their Grants changed by nobody: no stored Grant says it. `Shipped` is the refusal that replaces `HelpReadOnly` and the rule above that refuses every change to "a System no Account owns", which an Organization's System would otherwise fall under.
