# database

Every table hexframe keeps, and the one way to reach them: the `Database` service, Drizzle's query builder over `@effect/sql-pg`. Deployed, it talks to Neon, one branch per pull request; in tests, to PGlite, a real Postgres in memory. Both get the same migrations, applied by the same migrator. Which Drizzle build and why is `hexframe-v0-server-foundations/decisions.md#DEC-7` in the run's registers.

| File | Holds |
|---|---|
| `database.ts` | `Database`, the service, and `layer`, the deployed one, built from `DATABASE_URL`; `transactional`, which runs a program in one transaction every repository's query joins, and `InTransaction`, what a call that only holds inside one requires; `AfterCommit`, what the program defers to the commit, run once it commits, in order, dropped on a rollback, and handed to the outer transaction's commit by one opened inside another |
| `promise.ts` | `PromiseDatabase` and its deployed `layer`: the same database through Drizzle's promise API over a node-postgres pool, for Better Auth's adapter. Only `auth/` may import it, and this folder's harness and tests |
| `schema.ts` | The tables, in Drizzle's schema language: IAM's, in Better Auth's shape and under its names, its api-key plugin's `apikey` among them, with a key to `user` the plugin's own schema lacks ([[4-software-engineering/1-projects/1-hexframe/1-app/src/repositories/auth/CLAUDE\|auth]]); Mapping's `tile`, a Tile or a Reference per row, with the Name, Tile config (`TileConfigColumn`) and Frontmatter (`FrontmatterColumn`) an imported file carried, each null when it carried none, the Tile's `version`, 1 when the row is added, which Mapping decides and writes, and, on the Root's row, the System's `system_version`, 0 when added, which Mapping decides and writes too; Assistant's `conversation`, one per Account at most, with the `mode` its Turns take, `ask` until switched, `conversation_entry`, an Entry at the instant it dates from, its content the JSON Assistant encodes, `seq` ordering two of one instant as they were written, `turn`, a Turn answering one Entry, the `mode` it started in, `apply` for those before Modes, what it spent and what its calls under way reserved, its agent's step, as Assistant encodes it, null between steps, how and when it ended null while it runs, `turn_running_idx` letting one run at most per Conversation, and `proposal`, the writes a Turn drafted in ask, its `drafts` as Assistant encodes them, its Entry and the Turn that opened it, how and when the user decided it null while it is open, `proposal_open_idx` letting one be open at most per Conversation, and `applied`, what an applied Turn or an accepted Proposal applied, by its id, what undoes it as Assistant hands it, its changes, the Entry that offers it, null while a Turn runs, and when it was undone, null until then; and IAM's own `turn_key`, a Turn's Key by its secret's SHA-256, bound to its Account, which deleting deletes it with, and to a Turn, by its id, with no key to it, until it expires |

It keeps a Mode, a fate and the drafts as given; Assistant decodes them. And `applied.ts`, `Applied` and its `layer`: inside a transaction, what one of the Account's Turns or Proposals applied, by its id, its row locked (`locked`), kept, added or set whole (`keep`), the Entry that offers to undo it set (`offer`), and marked undone (`undone`). It keeps what undoes them as given, which Assistant hands on, opaque, and decides whether they may be undone. `testing.ts`, for tests only, what no program of the app does: a Turn's start moved back, an Account's Turns made to have spent a sum, whether a Turn's Key is still kept, the Tile a Turn started in, and whether the transaction a test runs in locked an Account's Conversation's row |

## Changing the schema

1. Edit `schema.ts`.
2. `pnpm db:generate --name <what-changed>` writes the next migration into `migrations/` (drizzle-kit, `drizzle.config.ts`). Commit it with the schema; never edit a migration once it has landed.
3. `pnpm test` runs it against PGlite.
4. Push. Each Vercel deployment runs `pnpm db:migrate` before it builds (`vercel.json`), against the Neon branch Neon's Vercel integration gives it: `preview/<git branch>`, forked from `main` on the branch's first deployment, on a preview; `main` in production. A build whose migration fails never goes live. When the pull request closes or the branch is deleted, `.github/workflows/hexframe-previews.yml` deletes its Neon branch: the free plan holds 10, and a full project fails every new preview. `pnpm db:migrate` by hand applies them to whatever `DATABASE_URL` names.

Production migrates before its new code serves, while the old code still does: a migration that lands on `main` must keep the code before it working (add a column, backfill, then drop the old one in a later change).

A deployed database changes through committed migrations only; `drizzle-kit push` is for a local one.

## Testing on the database

An integration test provides `TestDatabase` to the program under test, with `@effect/vitest`:

```ts
import { layer } from '@effect/vitest'
import { Effect } from 'effect'

import { Database } from '#/repositories/database/database'
import { TestDatabase } from '#/repositories/database/testing'

layer(TestDatabase)('the tiles repository', (it) => {
  it.effect('reads back what it wrote', () =>
    Effect.gen(function* () {
      const database = yield* Database
      // ...
    }),
  )
})
```

Each build of the layer is a new, empty database: the tests inside one `layer(...)` block share it, two blocks never do. In a test run it starts from the run's template, a data directory already migrated, rather than running PGlite's initdb and every migration again: with every test file building one at once, that initdb alone took seconds, past a test's timeout. `migrated` still runs on it, a no-op. Under `pnpm dev`, with no template, it starts empty and is migrated.

## Rules

- **Only this folder imports `drizzle-orm`, `@effect/sql-pg`, `@effect/sql-pglite`, `pg`, `@electric-sql/pglite` and Neon's `@neondatabase/*`**, should one be needed (`dependency-cruiser.config.ts`).
- **`Database` for every repository; `PromiseDatabase` only for Better Auth's adapter, which awaits its queries.** `dependency-cruiser.config.ts` keeps `promise.ts` to `auth/` and this folder, whose `testing.ts` provides both over one PGlite. Both reach the same Postgres and the same tables, so a row Better Auth writes is one a later repository reads with `Database`.
- **A repository never opens a transaction; the API layer does, with `transactional`.** Effect's SQL client carries the open transaction along with the running program, so every query made through `Database` inside it joins it, whichever repository makes it: nothing is passed down. A call that is wrong outside one, a lock or a write, requires `InTransaction`, so the compiler refuses a program that makes it without the API having opened one. Work that must not run before the commit, as the bus's publishes, is deferred through `AfterCommit`, which knows nothing of what it runs. Better Auth's writes go through `PromiseDatabase`, its own pool, and join no such transaction.
- **The query builder, never raw SQL.** It is the security bar, and it is also what keeps the two drivers alike: Drizzle's `db.execute` returns rows as an array over `effect-postgres` and as `{ rows }` over `effect-pglite`, while a `select` returns the same array on both.
- **`node scripts/migrate.ts` runs `database.ts` and `migrations.ts` without a bundler.** `database.ts` imports packages only, and `migrations.ts` imports it as `./database.ts`, the one `.ts` import path the lint allows under `src/`. `scripts/migrate.test.ts` proves the script loads. `testing.ts` is for tests, and for `pnpm dev` without `DATABASE_URL` (`src/api/server/run.ts` imports it behind `import.meta.env.DEV`): a build never holds it.
- **The server function runtime builds `Database` under the tiles repository.** Deployed, `src/api/server/run.ts` builds the deployed `Database` beside Better Auth, which reaches Postgres through its own `PromiseDatabase`. Under `pnpm dev` and the tests, `TestAuth` brings `TestDatabase`, which holds both over one PGlite, and the tiles repository reads and writes it.
